## 1. Background

### BT-1..4: Why agents kept burning 10 minutes on full-genome BLAST

After the hb002 validation run with gpt-oss-120b on Cerebras, trajectory analysis revealed a
consistent pattern across all three attempts: the agent's very first BLAST call used the entire
genome FASTA file (≈4 MB, roughly 4 million bp) as the query. Remote BLAST has a practical
ceiling of ~1500 bp for reliable results; any query larger than this will time out after 10
minutes (the `step_timeout_seconds=600` hard limit per command). Two of the three attempts
eventually recovered by progressively downsizing the query; the third exhausted its 3600-second
wall-clock budget cycling through increasingly corrupt query files.

Two harness problems contributed:

1. **No pre-flight size check.** The harness dispatched every BLAST query regardless of its
   size. A 4 MB query consumed 600s of wall-clock budget before returning rc=-1.

2. **System prompt lied about wall-clock limits.** The prompt said: *"Note: there is no
   wall-clock time limit on this run."* This was false — `config.run_timeout_seconds = 3600`
   is a soft limit checked at every loop iteration. An agent told there is no time limit has
   no incentive to stop retrying a failing approach. Attempt 2 reached 3769 seconds before
   the loop's wall-clock check terminated it.

### RV-1..4: Why gpt-oss-120b's reasoning was invisible

gpt-oss-120b uses OpenAI's **Harmony format** — a channel-multiplexed output scheme where the
model writes to three separate channels:

- `analysis` — chain-of-thought (CoT) reasoning, hidden from end users in most UIs
- `commentary` — tool calls and structured outputs
- `final` — the visible text response shown to the user

When served through the Cerebras **Chat Completions API** (the `/chat/completions` endpoint),
Harmony tokenisation is handled internally by the inference layer. The API response collapses
the channels into a standard `ChatCompletion` object:

- `msg.content` → **only** the `final` channel text (empty during tool-call steps)
- `msg.reasoning` → the `analysis` channel CoT (Cerebras-specific field, `text_parsed` format)
- `msg.tool_calls` → the `commentary` channel tool calls

The harness read `msg.content` and `msg.tool_calls` but never read `msg.reasoning`. Every
trajectory therefore showed blank "Agent reasoning" sections — the CoT existed in the API
response but was discarded.

Additionally, no `reasoning_effort` parameter was sent, leaving Cerebras on its default
`"medium"` reasoning depth. For hard bioinformatics problems, `"high"` is appropriate.

> **📦 Harmony format**
> Harmony is OpenAI's native chat format for gpt-oss-120b. It uses special token delimiters
> to separate three output channels (`<|analysis|>`, `<|commentary|>`, `<|final|>`). Inference
> providers that expose a Chat Completions API (Cerebras, Ollama, vLLM) handle the delimiters
> internally — you never see them in the response. The result appears as a normal
> `ChatCompletion` with an extra `reasoning` field. Only native Harmony users (calling the
> model directly without a provider layer) need to manage the delimiters themselves.
> Further reading: [OpenAI Harmony cookbook](https://developers.openai.com/cookbook/articles/openai-harmony)

## 2. BT-1 — Query-size cap in `_blast_search()`

**Files:** `harness/config.py`, `harness/agent.py`

A new `RunConfig` field gates the pre-check:

```python
# harness/config.py
blast_max_query_bp: int = 1500  # 0 = disabled
```

In `harness/agent.py`, before dispatching any remote BLAST call, the harness counts the query
length using `awk` inside the container:

```python
# harness/agent.py — inside _blast_search(), remote BLAST path
awk_cmd = (
    f"awk 'NF && !/^>/{{n+=length($0)}} END{{print n+0}}' {query}"
)
bp_out, _, bp_rc = self.container.exec_command(awk_cmd, timeout=10)
bp_count = int((bp_out.strip() or "0"))

if self.config.blast_max_query_bp > 0 and bp_count > self.config.blast_max_query_bp:
    msg = (
        f"rc=-1: Query too large ({bp_count} bp). Remote BLAST times out on queries "
        f">{self.config.blast_max_query_bp} bp.\n"
        f"Extract a ≤500 bp subsequence and retry."
    )
    self.logger.log("tool_call", {"blast_command": f"[size-check refused] {query}"})
    self.logger.log("tool_result", {"blast_command": ..., "summary": msg, "returncode": -1})
    # ... return synthetic tool_result to agent
    return
```

The awk command counts non-header nucleotide characters (skips lines beginning with `>`). If
the count exceeds the cap, the harness returns immediately with a synthetic rc=-1 message
explaining the size limit and directing the agent to extract a shorter sub-sequence. No
network call is made.

Setting `blast_max_query_bp = 0` disables the pre-check entirely (useful for testing or
local BLAST against a custom database).

## 3. BT-2 — Correcting the wall-clock claim in system.txt

**File:** `prompts/system.txt`

The "Step and context budget" section previously contained:

> *"Note: there is no wall-clock time limit on this run."*

This was replaced with:

> *"Note: **this run has a 60-minute wall-clock time limit** in addition to the step limit.
> Each remote BLAST call that times out consumes up to 10 minutes of that budget."*

The real limit (`run_timeout_seconds = 3600`) was always enforced — the prompt simply
misstated it. With the correct information, the agent can trade off step count vs. wall-clock
time when deciding whether to retry a BLAST call.

## 4. BT-3 — Elapsed time in `_progress_footer()`

**File:** `harness/agent.py`

`_progress_footer()` (module-level helper, ~line 860) gains two optional parameters:

```python
def _progress_footer(
    step: int,
    max_steps: int,
    input_tokens: int,
    elapsed_seconds: float = 0.0,
    run_timeout_seconds: int = 0,
) -> str:
```

When `run_timeout_seconds > 0`, the footer includes `elapsed Xs/3600s`:

```
[Progress: step 42/100 | elapsed 1842s/3600s | context ~45k tokens | 58 steps remaining]
```

Urgency messages now fire on **either** step-count or wall-clock consumption, whichever
triggers first:

| Threshold | Message |
|-----------|---------|
| ≥75% steps or ≥75% wall-clock | `⚠ WARNING: N steps / Xs wall-clock remaining. Each BLAST timeout costs 10 min. Switch to a confirmed working approach.` |
| ≥90% steps or ≥90% wall-clock | `⚠ CRITICAL: State your FINAL ANSWER immediately.` |

All call sites in `_loop` pass `elapsed_seconds=time.monotonic() - start` and
`run_timeout_seconds=self.config.run_timeout_seconds`.

## 5. BT-4 — Rewriting the blast-search SKILL opening

**File:** `SKILLS/blast-search/SKILL.md`

The existing SKILL had query-size guidance buried in the middle. BT-4 moves it to the top
as a prominent `⚠ CRITICAL` block:

```markdown
## ⚠ CRITICAL: Always start with a short query (≤500 bp)

**Never BLAST the full genome or any sequence >1500 bp remotely — it will always time out.**
```

The size table is updated from the old "≤5000 bp safe" to the harness reality:
- **≤500 bp** — ideal; returns in 3–8 minutes
- **500–1500 bp** — acceptable; may take 5–10 minutes  
- **>1500 bp** — refused by the harness immediately

## 6. RV-1 — `reasoning_effort` API parameter

**Files:** `harness/config.py`, `harness/llm.py`, `scripts/run_eval.py`

`RunConfig` gains a `reasoning_effort` field:

```python
# harness/config.py
reasoning_effort: str = "high"  # empty = omit from API call
```

`OpenAIProvider.__init__` accepts and stores it:

```python
# harness/llm.py
class OpenAIProvider(Provider):
    def __init__(self, api_key, base_url=None, reasoning_effort=""):
        ...
        self._reasoning_effort = reasoning_effort
```

`OpenAIProvider.chat()` passes it to the API when non-empty:

```python
effort = getattr(self, "_reasoning_effort", "")
if effort:
    kwargs["reasoning_effort"] = effort
```

`build_provider()` forwards it:

```python
def build_provider(provider, api_key, base_url=None, judge_model="", reasoning_effort=""):
    ...
    p = OpenAIProvider(api_key=api_key, base_url=base_url, reasoning_effort=reasoning_effort)
```

`run_eval.py` exposes a CLI flag:

```bash
--reasoning-effort [high|medium|low|""]   # default: high
```

The empty-string choice lets callers explicitly omit the parameter (e.g. for providers that
don't support it).

> **Note on `getattr` defence:** `OpenAIProvider` is instantiated in some tests via
> `OpenAIProvider.__new__(OpenAIProvider)`, which bypasses `__init__`. Direct attribute
> access (`self._reasoning_effort`) would raise `AttributeError` in those test stubs.
> `getattr(self, "_reasoning_effort", "")` is safe for both paths. See §L-30.

## 7. RV-2 — Reading `msg.reasoning` from Cerebras responses

**File:** `harness/llm.py`

`LLMResponse` gains a new field:

```python
@dataclass
class LLMResponse:
    ...
    reasoning: str = ""  # CoT from msg.reasoning (OpenAI) or thinking blocks (Anthropic)
```

`openai_response_to_llm_response()` extracts it:

```python
raw_reasoning = getattr(msg, "reasoning", None) or getattr(msg, "reasoning_content", None) or ""
reasoning = raw_reasoning if isinstance(raw_reasoning, str) else ""
return LLMResponse(..., reasoning=reasoning)
```

Two attribute names are checked (`reasoning` and `reasoning_content`) to accommodate
potential API naming variations across Cerebras versions.

`_anthropic_response_to_llm_response()` handles Anthropic extended-thinking `thinking` blocks:

```python
elif btype == "thinking":
    thinking_parts.append(
        block.thinking if hasattr(block, "thinking") else block.get("thinking", "")
    )
...
return LLMResponse(..., reasoning="\n".join(thinking_parts))
```

This provides a uniform `LLMResponse.reasoning` interface across both providers, regardless
of whether the CoT comes from Cerebras's `msg.reasoning` or Anthropic's extended thinking.

## 8. RV-3 — Logging and rendering reasoning

**Files:** `harness/agent.py`, `scripts/trajectory_to_md.py`

### JSONL trajectory logging

The main loop previously logged:

```python
self.logger.log("assistant", {
    "reasoning": response.text,  # was the final-channel text, misleadingly named
    "content": response.raw_content,
    ...
})
```

Now it logs the actual CoT, only when non-empty:

```python
log_entry = {
    "stop_reason": response.stop_reason,
    "content": response.raw_content,
    "usage": {...},
}
if response.reasoning:
    log_entry["reasoning"] = response.reasoning
self.logger.log("assistant", log_entry)
```

For Anthropic, `response.reasoning` is `""` unless extended thinking is enabled, so the
field is simply absent from those JSONL events.

### trajectory_to_md.py fixes

Three bugs in the Markdown converter were fixed in the same pass:

**Bug 1 — Reasoning rendered as `<details>` block:**

```python
# Before: no reasoning field was rendered
# After:
reasoning = data.get("reasoning", "")
if reasoning:
    lines.append("<details><summary>Reasoning</summary>\n")
    lines.append(reasoning.rstrip())
    lines.append("</details>\n")
```

**Bug 2 — `blast_search` tool calls rendered as empty bash blocks:**

The `tool_call` event for `blast_search` uses key `"blast_command"` (not `"command"`).
The converter was doing `data.get("command", "")`, which returned `""` for every BLAST call.

```python
# After:
is_blast = "blast_command" in data
cmd = data.get("blast_command") if is_blast else data.get("command", "")
label = "BLAST" if is_blast else "Command"
```

**Bug 3 — BLAST tool results showed no output:**

The `tool_result` event for `blast_search` uses key `"summary"` (not `"stdout"`). The
converter was checking only `data.get("stdout")`.

```python
# After:
stdout = (data.get("stdout") or data.get("summary") or "").rstrip()
```

## 9. RV-4 — Harmony reasoning directive in system message

**File:** `harness/llm.py`

The Harmony article documents that placing `Reasoning: high` in the system message activates
maximum CoT depth when running natively. For the Chat Completions path the `reasoning_effort`
API parameter (RV-1) is the primary mechanism, but the directive is added as belt-and-suspenders:

```python
def chat(self, model, system, messages, tools, max_tokens, logger=None):
    effort = getattr(self, "_reasoning_effort", "")
    if effort and system:
        system = system + f"\n\nReasoning: {effort}"
    oai_messages = anthropic_to_openai_messages(messages, system)
    ...
```

This happens before the system message is converted to OpenAI wire format, so the directive
appears in the `{"role": "system", "content": "..."}` message. Cerebras accepts `system` as
an alias for the Harmony `developer` role, so no role change is needed.

## 10. Data-flow diagram

```
run_eval.py --reasoning-effort high --provider openai --model gpt-oss-120b
    │
    ├─ build_provider("openai", ..., reasoning_effort="high")
    │       └─ OpenAIProvider.__init__(reasoning_effort="high")
    │
    └─ AgentRun._loop()
            │
            ├─ client.chat(model, system, messages, tools, max_tokens)
            │       │  [OpenAIProvider.chat()]
            │       ├─ Append "\n\nReasoning: high" to system   [RV-4]
            │       ├─ Convert messages to OpenAI wire format
            │       ├─ Add reasoning_effort="high" to kwargs    [RV-1]
            │       ├─ client.chat.completions.create(**kwargs) → Cerebras API
            │       └─ openai_response_to_llm_response(response)
            │               ├─ msg.content  → LLMResponse.text    (final channel, often "")
            │               ├─ msg.tool_calls → LLMResponse.tool_calls
            │               └─ msg.reasoning → LLMResponse.reasoning  [RV-2]
            │
            ├─ logger.log("assistant", {"reasoning": resp.reasoning, "content": ...})  [RV-3]
            │
            ├─ for tool_call in response.tool_calls:
            │       └─ if blast_search:
            │               ├─ awk to count query bp              [BT-1]
            │               ├─ if bp > blast_max_query_bp: return synthetic rc=-1
            │               └─ else: exec blastn in container
            │
            └─ _progress_footer(step, max_steps, tokens,
                                elapsed_seconds=time.monotonic()-start,   [BT-3]
                                run_timeout_seconds=config.run_timeout_seconds)

JSONL trajectory → trajectory_to_md.py
    ├─ assistant event: reasoning → <details><summary>Reasoning</summary>  [RV-3]
    ├─ tool_call event: blast_command key → "BLAST" label                  [RV-3]
    └─ tool_result event: summary key → output block                       [RV-3]
```

## 14. Glossary

| Term | Definition |
|------|-----------|
| CoT | Chain-of-Thought — the model's internal reasoning trace, written to the `analysis` Harmony channel |
| Harmony | OpenAI's channel-multiplexed output format for gpt-oss-120b; three channels: `analysis`, `commentary`, `final` |
| `text_parsed` | Cerebras API's default response mode; CoT returned in a separate `msg.reasoning` field |
| `reasoning_effort` | Cerebras/OpenAI API parameter controlling reasoning depth (`low`, `medium`, `high`) |
| `blast_max_query_bp` | `RunConfig` field; remote BLAST queries larger than this are refused before dispatch |
| `msg.content` | OpenAI response field carrying the `final` Harmony channel — empty during tool-call steps for gpt-oss-120b |
| `msg.reasoning` | Cerebras-specific response field carrying the `analysis` Harmony channel (CoT) |
| `LLMResponse.reasoning` | Harness-internal field populated from `msg.reasoning` (Cerebras) or thinking blocks (Anthropic) |
