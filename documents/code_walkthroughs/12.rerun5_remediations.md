## 1. Background: what RERUN-5 revealed

RERUN-5 was a comparative benchmark run (Qwen3/Cerebras vs. earlier baseline) that exposed six categories of harness deficiency:

| Symptom observed in RERUN-5 | Root cause | Remediation |
|---|---|---|
| Docker rebuild did not detect changed SKILL files | No content-hash check; relied on `--no-cache` | SI: SHA-256 hash label on the image |
| Agent never referenced skill recipes despite them existing | Skill filenames not surfaced in initial message | SK: `ls /workspace/skills/` injected into env context |
| Attempt ended mid-`tool_use` with no final answer | Step limit fires at top of loop before `end_turn` | SL: inline extra API call at step limit |
| Agent aborted long downloads prematurely ("wall-clock timeout") | Abort criterion mentioned "run timeout"; no step-budget shown | TM: remove timeout criterion; inject step budget |
| Agent attempted manual genome assembly instead of documented recipes | No genome-retrieval SKILL file existed | GD: genome-retrieval, ucsc-sequence-fetch, blast-search SKILLs |
| Critic raised concerns not grounded in trajectory text | No citation requirement in prompt; truncation limits too tight | CA: CITATION GATE, wider truncation, critic-guidance SKILL |

All six slices are independent and can be merged in any order.

## 2. SI — Stale Docker Image Detection

**Files changed:** `scripts/run_eval.py` · `tests/test_ensure_docker.py` (new)

### The problem

Before SI, `ensure_docker_image()` checked only whether the image *existed*. If a developer added a new SKILL file to `SKILLS/` or modified the Dockerfile, the old image was silently reused — the new file was not present inside the container. The only workaround was to remember to pass `--no-cache` manually.

### Solution: build-hash label

`_compute_build_hash()` produces a 16-character SHA-256 hex digest over all files in `docker/` and `SKILLS/` (sorted paths):

```python
# scripts/run_eval.py
def _compute_build_hash(dockerfile_dir: Path) -> str:
    """SHA-256 of Dockerfile + all files under docker/ and SKILLS/ (sorted paths)."""
    h = hashlib.sha256()
    repo_root = dockerfile_dir.parent
    paths = sorted(
        p for p in dockerfile_dir.rglob("*") if p.is_file()
    ) + sorted(
        p for p in (repo_root / "SKILLS").rglob("*") if p.is_file()
    )
    for p in paths:
        h.update(p.read_bytes())
    return h.hexdigest()[:16]
```

The hash is embedded as a Docker image label at build time (`--label build_hash=<hash>`). On every subsequent run, `ensure_docker_image()` reads this label back and compares it to the current hash:

```python
# scripts/run_eval.py
def ensure_docker_image(
    image_name: str, dockerfile_dir: Path, force_rebuild: bool = False
) -> None:
    repo_root = dockerfile_dir.parent
    current_hash = _compute_build_hash(dockerfile_dir)
    inspect = subprocess.run(["docker", "image", "inspect", image_name], capture_output=True)
    if inspect.returncode != 0:
        needs_build = True          # image missing → build
    elif force_rebuild:
        needs_build = True          # --rebuild flag → force build
    else:
        stored_hash = subprocess.run(
            ["docker", "image", "inspect", "--format",
             "{{index .Config.Labels \"build_hash\"}}", image_name],
            capture_output=True, text=True,
        ).stdout.strip()
        needs_build = (stored_hash != current_hash)   # stale → rebuild

    if needs_build:
        subprocess.run(
            ["docker", "build", "-t", image_name,
             "--label", f"build_hash={current_hash}",
             "-f", str(dockerfile_dir / "Dockerfile"),
             str(repo_root)],       # build context = repo root (not docker/)
            check=True,
        )
```

> **📦 Docker image labels**
> Labels are arbitrary key-value string metadata baked into an image at build time (`--label key=value`). They survive image re-tags and can be read cheaply without starting a container: `docker image inspect --format '{{index .Config.Labels "key"}}' image_name`. The label approach avoids parsing `docker history` or maintaining an out-of-band state file.

### --rebuild flag

A `--rebuild` CLI flag bypasses the hash check and forces a fresh build unconditionally:

```python
# scripts/run_eval.py
@click.option("--rebuild", is_flag=True,
              help="Force Docker image rebuild even if hash matches.")
```

This is useful when a mid-session developer change is not yet committed (so the hash would be stale without the flag).

## 3. SK — Auto-inject Skills Directory

**Files changed:** `harness/agent.py` · `tests/test_agent_helpers.py`

### The problem

SKILL recipe files were baked into the container at `/workspace/skills/` by GM (PR #60), but agents were expected to run `ls /workspace/skills/` themselves to discover them. In practice, agents rarely ran this check unprompted. The files were present but invisible.

### Solution: listing injected into initial message

`_get_environment_context()` now runs `ls /workspace/skills/` inside the container and appends the result to the environment context block that is prepended to the first user message:

```python
# harness/agent.py
# SK-1: inject skills directory listing so agents see available recipes immediately
try:
    skills_stdout, _err, _rc = self.container.exec_command(
        "ls /workspace/skills/ 2>/dev/null || true", timeout=10
    )
    listing = skills_stdout.strip()
except Exception:
    listing = ""

if listing:
    context += f"\n\n## Available bio method recipes\n{listing}"
else:
    context += "\n\n## Available bio method recipes\n(none — /workspace/skills/ is empty)"
```

The agent therefore sees, before reading the problem question, something like:

```
## Available bio method recipes
blast-search.md
chipseq-tf-identification.md
deg-functional-enrichment.md
genome-retrieval.md
ucsc-sequence-fetch.md
```

The system prompt pointer was updated to match: the old instruction `"Run ls /workspace/skills/"` was replaced with `"The available recipes are listed in the environment context at the start of this run."`.

## 4. SL — Step-limit Answer Extraction

**Files changed:** `harness/agent.py` · `tests/test_agent_helpers.py` · `SKILLS/code-learnings/SKILL.md`

### The problem

`_loop()` checked `self.steps >= self.config.max_steps` at the **top** of the while loop — before any API call. When the agent was in the middle of a multi-tool sequence and hit the limit, the run terminated with `status="max_steps"` while `stop_reason="tool_use"` was the last state. No final answer was extracted; the trajectory logged the last tool result as the final message.

This was confirmed in RERUN-5: `recq_a1` ended during a `pip install` step with no extractable answer.

### Solution: inline one-shot extraction

A flag `_step_limit_prompted` (initialised to `False` in `__init__`) prevents re-entry. When `steps >= max_steps` and `stop_reason == "tool_use"` and the flag is not set, the harness:

1. Appends `STEP_LIMIT_PROMPT` as a user message.
2. Makes one extra `client.chat(max_tokens=512)` call inline.
3. If the extra call returns `end_turn` → applies a one-shot FA check and returns `status="success"`.
4. If the extra call returns `tool_use` again → returns `status="max_steps"` (guard fires).

```python
# harness/agent.py (inside _loop, tool_use branch)
if self.steps >= self.config.max_steps and not self._step_limit_prompted:
    self._step_limit_prompted = True
    self.messages.append({
        "role": "user",
        "content": [{"type": "text", "text": STEP_LIMIT_PROMPT}],
    })
    sl_resp = self.client.chat(
        model=self.config.model,
        system=self.system_prompt,
        messages=self.messages,
        tools=[BASH_TOOL, ABORT_TOOL, BLAST_TOOL],
        max_tokens=512,
        logger=self.logger,
    )
    # ... token accounting ...
    if sl_resp.stop_reason == "end_turn":
        # FA check + return success if marker found
        ...
        return AgentResult(status="success", ...)
    # sl_resp was still tool_use → guard fires on next iteration
    return self._result("max_steps", start)
```

`STEP_LIMIT_PROMPT` is a module-level constant:

```python
STEP_LIMIT_PROMPT = (
    "You have reached the step limit. "
    "You MUST state your best answer immediately. "
    "Do not call any more tools. "
    "Respond with only: FINAL ANSWER: <your answer>"
)
```

> **Why inline, not via `continue`?**
> If the code appended the prompt and then called `continue`, the loop's top-of-iteration check (`steps >= max_steps`) would fire *again* before the extra API call. The extra call would never be made. Handling the entire extraction inline — calling the API, processing the response, and returning — avoids re-entering the loop guard. This is recorded in L-24 of `SKILLS/code-learnings/SKILL.md`.

## 5. TM — Fix Time/Step Messaging

**Files changed:** `prompts/system.txt` · `harness/agent.py` · `tests/test_agent_helpers.py`

### The problem

Three separate messaging issues caused agents to make poor step-budget decisions:

1. The system prompt's §Step 4 listed `"The analysis would take so long on available CPUs that it would exceed the run timeout"` as a valid abort criterion. This caused agents to abort long downloads citing a wall-clock limit that does not exist in the harness.
2. The ≥75% WARNING in the system prompt told agents to stop and draft a final answer immediately — even if an in-progress download was almost complete.
3. Agents did not know how many steps they had total. The step budget was described in the system prompt text but not injected as a concrete number at runtime.

### Solution

**TM-1:** The timeout abort criterion was removed from §Step 4. Agents can still call `abort` for RAM/disk/CPU constraints; wall-clock duration is explicitly not a criterion.

**TM-2:** `_get_environment_context()` now appends a `## Step budget` block with concrete numbers:

```python
# harness/agent.py
context += (
    f"\n\n## Step budget\n"
    f"Step budget: {self.config.max_steps} steps total "
    f"(1 tool call = 1 step, regardless of wall time)\n"
    f"Per-command timeout: {self.config.step_timeout_seconds}s "
    f"(downloads may use this fully — it is fine)"
)
```

The phrase `"regardless of wall time"` directly counters the false belief that downloads cost extra time budget.

**TM-3:** The ≥75% WARNING was softened from `"Begin drafting your final answer. Do not start new lines of investigation."` to:

> *"You are approaching the step limit. If a download or multi-step computation is already underway and likely to complete within the remaining steps, continue it. Otherwise, consolidate what you already know and begin drafting your final answer. Do not start entirely new lines of investigation."*

## 6. GD — Genome Download Skills

**Files changed:** `SKILLS/genome-retrieval/SKILL.md` (new) · `SKILLS/ucsc-sequence-fetch/SKILL.md` (new) · `SKILLS/blast-search/SKILL.md` (new) · `docker/Dockerfile` · `scripts/smoke_test_container.py` · `prompts/system.txt` · `tests/test_agent_helpers.py`

### The problem

RERUN-5 showed agents reinventing genome-download approaches from scratch on each attempt — sometimes correctly, often not. The `recq` problem requires downloading a reference genome sequence, but no documented recipe existed. Similarly, agents confused by empty BLAST results had no troubleshooting reference.

### Three new SKILL files

**`SKILLS/genome-retrieval/SKILL.md`** — two recipes:
- Recipe A: `nohup wget -q <url> -O <file> & PID=$!` background download with `wait $PID` polling loop (EBI, Gencode, Ensembl, NCBI fallbacks)
- Recipe B: UCSC per-chromosome FASTA download when only specific chromosomes are needed

**`SKILLS/ucsc-sequence-fetch/SKILL.md`** — Python helper using the UCSC DAS REST API:
- `fetch_sequence(chrom, start, end, genome)` for individual intervals
- Batch-from-BED function with 1 req/s throttle
- Guidance table: when to use REST vs. direct download

**`SKILLS/blast-search/SKILL.md`** — augmented from the existing blast-search SKILL:
- ⚠ PATH warning: `blastn` is installed in `/opt/conda/bin/blastn`, not the default `$PATH`; use the full path or `export PATH=/opt/conda/bin:$PATH`
- 16S species identification recipe
- Protein homology recipe
- 5-step empty-results troubleshooting checklist

### Docker integration

Three COPY directives were added to `docker/Dockerfile`:

```dockerfile
COPY SKILLS/genome-retrieval/SKILL.md /workspace/skills/genome-retrieval.md
COPY SKILLS/ucsc-sequence-fetch/SKILL.md /workspace/skills/ucsc-sequence-fetch.md
COPY SKILLS/blast-search/SKILL.md /workspace/skills/blast-search.md
```

The total skill count in `/workspace/skills/` went from 2 to 5. The smoke test count check was updated accordingly:

```python
# scripts/smoke_test_container.py
_EXPECTED = {..., "skill_count": "5"}
```

### System prompt pointers

Three lines were added to §Environment details directing the agent to consult the skill files by name for genome retrieval, UCSC sequence fetching, and BLAST searches.

> **Note on build context:** The `docker build` invocation uses the repo root as the build context (`-f docker/Dockerfile .`), not the `docker/` subdirectory. This is required because `COPY SKILLS/...` paths resolve relative to the build context, and `SKILLS/` lives at the repo root.

## 7. CA — Critic Accuracy

**Files changed:** `harness/agent.py` · `SKILLS/critic-guidance/SKILL.md` (new, host-side only) · `tests/test_agent_helpers.py` · `tests/test_critic_grounding.py` (new)

### The problem

RERUN-5 critic analysis (walkthroughs 10/11) found three structural accuracy problems:

1. **Hallucinated citations** — the critic raised concerns not grounded in any agent step. Nothing in the prompt required a verbatim quote.
2. **Reasoning truncation too tight** — `_format_trajectory_for_critic()` truncated AGENT REASONING blocks at 400 chars and TOOL RESULT blocks at 600 chars. Multi-step reasoning was cut before the conclusion; tool results were cut before error messages.
3. **max_tokens too low** — the critic was capped at 1024 tokens, which prevented listing alternatives for HIGH-risk assumptions.

### CA-1: CITATION GATE in prompts

A `CITATION GATE` block was prepended to `CRITIC_SYSTEM_PROMPT` immediately after the opening paragraph, before the numbered instructions:

```
CITATION GATE — Before raising any concern, locate the exact agent step where
the claim was made. You MUST quote it as: 'Step N says: ...<verbatim>...'
If you cannot find the quote in the trajectory above, do not raise the concern.
Absence of a citation means the claim is your inference, not the agent's — omit it.
```

A matching gate was added to `CRITIC_FOLLOWUP_PROMPT` for the second-round review.

### CA-2: Wider truncation limits

In `_format_trajectory_for_critic()`:
- AGENT REASONING truncation: `text[:400]` → `text[:1500]`
- TOOL RESULT truncation: `str(result)[:600]` → `str(result)[:2500]`

These limits were chosen to keep the critic context window manageable (~30 steps × 4000 chars each) while preserving enough of each block to allow accurate citation.

`max_tokens` in `_run_critic()` was raised from `1024` to `2048` to accommodate the improved alternatives section for HIGH-risk flags.

### CA-3 and CA-4: _load_critic_skill()

A new host-side-only SKILL file (`SKILLS/critic-guidance/SKILL.md`) contains:
- Reiteration of citation requirements
- Structured output template: `ASSUMPTION [HIGH|MEDIUM|LOW]: Agent said (Step N): "<quote>"`
- 3-item pre-flight checklist
- Known RERUN-5 hallucination patterns with concrete examples

The method `_load_critic_skill()` reads this file, strips YAML frontmatter, and returns the body:

```python
# harness/agent.py
def _load_critic_skill(self) -> str:
    skill_path = Path(__file__).parent.parent / "SKILLS" / "critic-guidance" / "SKILL.md"
    try:
        text = skill_path.read_text()
    except FileNotFoundError:
        return ""
    import re as _re
    body = _re.sub(r"^---\n.*?\n---\n?", "", text, flags=_re.DOTALL)
    return "\n\n" + body.strip()
```

`_run_critic()` appends the skill body to the base system prompt:

```python
# harness/agent.py
full_system = system_prompt + self._load_critic_skill()
```

> **Why host-side only?**
> `critic-guidance` is operational guidance for the critic model, not analysis guidance for the agent. Baking it into the Docker image would make it visible to the agent (which reads `/workspace/skills/`), potentially causing the agent to second-guess itself based on critic instructions. Keeping it host-side keeps the two prompting surfaces clean.

> **Graceful degradation:** If `SKILLS/critic-guidance/SKILL.md` is missing (e.g. in a test environment without the SKILLS tree), `_load_critic_skill()` returns `""` and `full_system` equals `system_prompt` exactly — no crash, no change in behavior.

## 8. End-to-end data flow

This diagram shows a single attempt with all six RERUN-5 remediations active:

```
run_eval.py main()
  │
  ├── ensure_docker_image()  [SI]
  │     _compute_build_hash(docker/)
  │       └── SHA-256(docker/*, SKILLS/*)  → 16-char hex
  │     docker image inspect → read "build_hash" label
  │     if stale: docker build --label build_hash=<hash> -f docker/Dockerfile .
  │
  ├── AgentRun.__init__()
  │     self._step_limit_prompted = False
  │     self.critic_client = ...
  │
  └── AgentRun.run()
        │
        ├── _get_environment_context()  [SK, TM]
        │     exec_command(RESOURCE_CHECK_CMD)  → RAM/disk/CPU
        │     exec_command("ls /workspace/skills/")  [SK] → file listing
        │     append "## Step budget: N steps total..."  [TM]
        │     → context prepended to first user message
        │
        ├── _loop()
        │     while True:
        │       client.chat(model, system, messages, tools, max_tokens)
        │       │
        │       ├── stop_reason == "end_turn":
        │       │     _has_final_answer_marker() → FA check
        │       │     if critic injection point → _run_critic()  [CA]
        │       │                                    full_system = CRITIC_SYSTEM_PROMPT
        │       │                                               + _load_critic_skill()
        │       │                                    critic_client.chat(max_tokens=2048)
        │       │     return success
        │       │
        │       └── stop_reason == "tool_use":
        │             dispatch bash/abort/blast tools
        │             append tool_results to messages
        │             if steps >= max_steps and not _step_limit_prompted:  [SL]
        │               _step_limit_prompted = True
        │               append STEP_LIMIT_PROMPT
        │               sl_resp = client.chat(max_tokens=512)
        │               if sl_resp.end_turn → return success
        │               else → return max_steps
        │
        └── logger.log("status", ...)
```

```bash
  --critic-injection-points after_critic_response \
  --max-critic-rounds 2 \
  --critic-model claude-haiku-4-5-20251001 \
  --dataset preview --n-attempts 5
```

The Cerebras model runs the agent; the Anthropic Haiku model runs the critic. Both use the same agent loop and trajectory; only the `critic_client` differs.

## 12. Glossary

| Term | Expansion / meaning |
|---|---|
| SI | Stale Docker Image — remediation slice for hash-gated image rebuilds |
| SK | Skills auto-injection — remediation slice for surfacing SKILL filenames in env context |
| SL | Step-limit answer extraction — remediation slice for recovering an answer when `max_steps` fires mid-`tool_use` |
| TM | Time/step messaging — remediation slice for correcting wall-clock abort criterion and injecting step budget |
| GD | Genome download skills — remediation slice for genome-retrieval, ucsc-sequence-fetch, blast-search SKILL files |
| CA | Critic accuracy — remediation slice for CITATION GATE, truncation limits, and critic-guidance SKILL |
| SKILL | A Markdown recipe file in `SKILLS/*/SKILL.md`. Agent-facing SKILLs are baked into `/workspace/skills/` in the Docker image; host-side SKILLs are read by harness Python code only. |
| CITATION GATE | Block of text in `CRITIC_SYSTEM_PROMPT` requiring the critic to quote verbatim trajectory text before raising a concern |
| SHA-256 | Secure Hash Algorithm 256-bit — the hash function used for build-hash computation |
| FA | Final Answer — the `FINAL ANSWER: <answer>` marker the agent must include before `_loop` can return `status="success"` |
| RERUN-5 | The fifth benchmark re-run iteration; used here as the label for this wave of remediation slices |
| DAS | Distributed Annotation System — the UCSC REST API endpoint used by `ucsc-sequence-fetch` |
| YAML frontmatter | The `---\n...\n---` block at the top of SKILL files; stripped before injection into model prompts |
