## Summary of findings

1. **Qwen3 pass@1 = 0% is caused by first-attempt failures specific to each problem** —
   data access issues (hb020), API backoff disruption (hb002), and missing "FINAL ANSWER:"
   format (recqgsfxqqodhjens). These are recoverable on later attempts, which is why
   pass@5 = 60%.

2. **hb022 is a scorer bug, not a model failure** — both Sonnet and Qwen3 regularly
   produce the correct answer (`[Sample_01..Sample_08]`) but the LLM judge scores it
   wrong. This problem should not contribute to the "unsolvable" count until the scorer
   is fixed.

3. **Qwen3 is highly sensitive to backoffs** — when a 429 retry fires mid-analysis
   (especially on attempt 1), Qwen3 tends to give up or guess, while Sonnet retries
   the same logical path and usually succeeds.

4. **hb053 (heat stress) is a genuine hard problem** — both models fail all 5 attempts.
   Sonnet burns 90–99 steps per attempt at $2/attempt, using nearly half the total run
   budget on a single unsolvable problem. A step cap of 30 (not the apparent ~100 used
   here) would cut cost dramatically.

5. **Cleaning introduced one difference** — Qwen3 hb002 attempt 4 (resource_abort)
   shows `were_problems_introduced_by_cleaning=yes`. The stored predicted value in
   scores.json differs from what re-running `extract_final_answer` on the JSONL gives.
   No human-solvable problem was affected.

## Per-problem analysis

### hb020 — Qwen3 attempt 0: gave up in 45 seconds

Qwen3 a0: 33 steps, 45 seconds, predicted `"Unknown"`.

**What happened:** The trajectory analysis notes say "Agent correctly responded 'Unknown'
when no data was available." The agent appears to have either (a) not found the data
directory or (b) attempted a remote BLAST query, hit a backoff-related timeout,
and concluded there was no data. The 45-second wall time vs. ~300s for successful
attempts confirms the agent aborted early rather than fully exploring the problem.

**Why later attempts succeed:** Attempts 1 and 2 correctly identify `Homo sapiens` by
finding the MAPK14/p38α protein and comparing human-specific motifs. The structural
data was present; the first attempt just didn't reach it.

**Recommendation:** The system prompt rule "rc=0 + empty stdout means no results, not
tool absent" (SP-1/SP-2) may not have been enough to prevent early abort here. Consider
a more explicit "if you get empty results on the first try, verify data files are
present before concluding" instruction.

### hb002 — Qwen3 brittleness and the "Species X" attempt 0

Qwen3 attempt scores: `[F, F, T, F, resource_abort]`. Only attempt 2 correct
(predicted `Bacillus licheniformis`, 21 steps, 267s).

**Attempt 0 (backoff fired):** 1 API backoff, predicted `"Species X"` — a generic
placeholder. The backoff mid-analysis likely interrupted the model's reasoning about
16S rRNA similarity, causing it to give up with a non-answer.

**Attempt 1:** Predicted `Bacillus subtilis` — very close (same genus) but wrong.
The GC content (45.5%) and genome size (4.3 MB) are consistent with both *B. subtilis*
and *B. licheniformis*, so the model is making a reasonable but wrong guess.

**Attempt 2 (correct, 21 steps):** Shortest successful run. The model apparently found
a discriminating feature quickly — likely a specific gene or operon. Without reading
the trajectory in full, the brevity suggests a lucky BLAST hit or a specific sequence
feature the model recognised directly.

**Attempt 3 (wrong, 55 steps, $0.49):** The most expensive Qwen3 attempt. Predicted
`Bacillus cereus`. 55 steps suggests the model explored extensively but converged on
the wrong answer, possibly because *B. cereus* is a common genome-analysis hit and the
discriminating features for *B. licheniformis* are subtle.

**Attempt 4 (resource_abort):** Claimed BLAST and related tools were missing. Per L-12,
rc=0 with empty stdout is not the same as tool absent. The model incorrectly diagnosed
missing tools and aborted rather than retrying with alternative approaches.

**Sonnet contrast:** All 5 Sonnet attempts correct. Sonnet consistently finds a
diagnostic 16S rRNA or gene signature in 14–29 steps.

### recqgsfxqqodhjens — The CTCF problem: Qwen3 attempts 1–4 all differ

Qwen3 attempt scores: `[F, F, F, F, T]`. Predicted answers: `""`, `MAZ`, `ETS2`,
`SP1`, `CTCF`.

**Attempt 0 — empty prediction, but trajectory mentions CTCF:**
The scores.json stores `predicted: ""` but the trajectory analysis notes "Agent
predicted CTCF which matches the expected answer; however stored as empty." This means
the agent identified CTCF somewhere in its reasoning but did **not** emit the answer
in `FINAL ANSWER: CTCF` format — likely returning an explanation without the required
marker. The harness's `extract_final_answer` fell back to the last non-empty line,
which was either blank or not a clean answer. This is a **format compliance failure**,
not a reasoning failure.

**Attempts 1–3 — wrong TFs (MAZ, ETS2, SP1):**
All are real transcription factors. The model is doing valid bioinformatics but
arriving at the wrong answer. CTCF is distinctive (CCCTC-binding factor, very
characteristic motif), but ChIP-seq peak analysis is stochastic — without the
blast_search tool making JASPAR/MEME lookups reliably, the model is guessing based
on peak shape and GC content. Each attempt takes ~1300–1960 seconds (22–32 min),
suggesting the model is doing substantial MEME/motif analysis each time.

**Attempt 4 — finally correct (CTCF, 28 steps, 1305s):**
The only attempt that converged correctly. Likely a different motif-search path.

**Sonnet contrast:** All 5 Sonnet attempts correct (100%). The CTCF motif problem is
apparently straightforward for Sonnet with the blast_search tool available, suggesting
Sonnet is using a more directed BLAST/motif lookup strategy that Qwen3 doesn't
replicate reliably.

**Recommendation:** Add explicit JASPAR/MEME database search guidance to the system
prompt for ChIP-seq/ATAC-seq problems. If Qwen3 reliably fails at motif lookup, a
structured wrapper (similar to blast_search) for MEME/JASPAR could help.

### hb022 — Scoring anomaly: both models answer correctly but score wrong

This problem (`human_solvable=False`) shows a genuine scorer issue.

**What the models predict:**
- Qwen3 a0, a1, a3, a4: `[Sample_01, Sample_02, ..., Sample_08]`
- Sonnet a2, a3: `[Sample_01, Sample_02, ..., Sample_08]`

**The rubric says:** `The answer is: Sample_01', 'Sample_02', ..., 'Sample_08'`

**Why it still scores wrong:**
The trajectory analysis labels Qwen3 a0/a1/a3/a4 as `objectively_correct=maybe` —
the LLM analyst is uncertain because the question text is truncated in scores.json
(the full question ends with "divided into two experimental conditions: Cond" — cut
off). The problem likely asks which samples belong to *a specific condition* (e.g.,
Condition A), and the expected answer is a subset of samples, not all 8. However, the
rubric as stored lists all 8. This creates an impossible scoring situation: the model
lists all 8 samples, the rubric says the answer is all 8 samples, but the LLM judge
still scores wrong.

**Most likely root cause:** The truncated question and rubric format mismatch means
the LLM judge is calling `NO` on format grounds (e.g., the expected answer uses
Python-string-literal quote format `'Sample_01'`, while the predicted uses
`[Sample_01, ...]` bracket format). The exact-match scorer does not match these two
formats, and the LLM judge is failing to recognise them as equivalent.

**Impact:** This problem is marked `human_solvable=False` so it doesn't affect
pass@1-on-human-solvable. But if the scorer is fixed, it could affect total pass@5.

**Recommendation:** Investigate the full question text via `scripts/show_problem.py hb022`
and verify whether the rubric is complete. If the rubric is genuinely "all 8 samples"
and the LLM judge is calling NO on format, add a format-normalisation step to the judge.

### hb053 — Cost overrun on an unsolvable problem

Both models: 0/5 correct. Correct answer: `Heat stress`.

**Sonnet cost breakdown (5 attempts):** $9.94 total, avg $2/attempt, 91–99 steps.
The run command used `--max-steps` at the default of 30 per the `RunConfig`, but the
actual steps recorded in scores.json are 27, 91–99, and 92 — well above 30. This
suggests the run used a higher `--max-steps` or the default was overridden. The
Brachypodium distachyon heat-stress problem is apparently sufficiently ambiguous that
Sonnet keeps exploring without converging, burning tokens at every step.

**Qwen3 cost:** $3.56 total, avg $0.71/attempt. Much cheaper per attempt because
Qwen3 exits earlier (either hits timeout or gives a quick wrong guess).

**What the models predict:**
- Sonnet: fungal stress, timeout (empty), phosphate starvation, high light stress, salt stress
- Qwen3: cannot be determined (attempt 0 hit 2 backoffs), drought stress, oxidative stress,
  drought stress, empty (error)

All predictions are plausible stresses for grass transcriptomes, but heat stress has
a specific signature (HSP gene family upregulation) that neither model is identifying.
This is a knowledge gap, not a tool failure.

**Recommendation:**
1. Set `--max-steps 30` explicitly when running future benchmarks to cap per-attempt
   cost on hard problems.
2. Add a note to the system prompt that HSP family genes (HSP70, HSP90, small HSPs) are
   canonical heat-stress markers in grass species.
3. Consider adding hb053 to a "known hard / human_solvable=False" exclusion list for
   cost-capped exploratory runs.

## Cross-cutting patterns

### Qwen3 first-attempt failure modes

| Problem | Attempt 0 failure cause | Recoverable? |
|---------|--------------------------|--------------|
| hb020 | Data not accessed; returned "Unknown" in 45s | Yes (3/5 later correct) |
| hb002 | API backoff disrupted reasoning; returned placeholder | Yes (1/5 later correct) |
| recqgsfxqqodhjens | Found correct answer but omitted FINAL ANSWER: marker | Yes (1/5 later correct) |
| hb022 | Answered correctly but scorer/judge failed | N/A (human_solvable=False) |
| hb053 | Hit 2 API backoffs; returned "cannot be determined" | No (0/5 any attempt) |

Qwen3's pass@1=0% is not a fixed ceiling — it is caused by first-attempt-specific
failures (backoffs, data access, format compliance) that later attempts avoid. This
suggests Qwen3 would benefit from:
- A warm-up step: always verify data files exist before starting analysis
- A stricter FINAL ANSWER: format enforcement in the system prompt
- Fewer concurrent API calls to reduce 429 frequency on attempt 1

### API backoff distribution (Qwen3 only)

| Problem | Attempt | Backoffs |
|---------|---------|---------|
| hb002 | 0 | 1 |
| hb020 | 1 | 1 |
| hb020 | 2 | 2 |
| hb020 | 3 | 2 |
| hb022 | 0 | 1 |
| hb053 | 0 | 2 |
| hb053 | 3 | 2 |
| recqgsfxqqodhjens | 1 | 1 |
| recqgsfxqqodhjens | 3 | 1 |

Total: 13 backoffs across 25 attempts. All occurred in Qwen3 (Sonnet: 0 backoffs).
The backoffs are correlated with failure — of the 8 failed attempts that had at least
one backoff, 7 were incorrect. The one backoff-affected correct attempt was hb020 a1.

**Recommendation:** Run Qwen3 benchmarks at off-peak hours, or add a `--max-parallel 1`
flag to avoid queue saturation. If Cerebras queue congestion persists, consider a
longer initial wait (90s instead of 60s) for first backoff.

### Cleaning issue (one occurrence)

Qwen3 hb002 a4 (`resource_abort`): `were_problems_introduced_by_cleaning=yes`.
The stored `predicted` value is the full resource_abort message, which contains bold
markdown. The re-extracted `cleaned_answer` strips the bold markers. This is the
`_clean_answer` function working correctly — the only "issue" is that scores.json
stored the un-cleaned version. No human-solvable problem was affected.
