## 1. Background and motivation

### What RERUN-6 was supposed to validate

RERUN-6 was the Qwen3-235B-A22B / Cerebras benchmark run that followed the RERUN-5
infrastructure remediations (SI/SK/SL/TM/GD/CA, all merged before this session). Its
purpose: confirm that the five improvements actually helped agent performance on the five
preview problems, particularly:

- **hb002** (Bacillus species ID from 16S rRNA): expected to benefit from the new
  `blast-search` SKILL file and the BE disambiguation ("No hits" vs "binary missing")
- **recq** (CTCF motif identification): expected to benefit from genome-retrieval SKILL + TM
  fixes removing the false "run timeout" signal
- **Critic grounding**: expected to benefit from CA CITATION GATE reducing hallucinated concerns

### What actually happened

RERUN-6 ran to completion (5 problems × 5 attempts, ~2.5 h, two Docker Desktop restarts
mid-run). hb002 scored **0/5** — worse than the RERUN-5 baseline — for all five attempts.
The trajectories showed BLAST returning "No BLAST hits found" on every attempt. Agents
spent 20–40 steps retrying BLAST variants before falling back to unreliable manual 16S
motif analysis, which produced wrong or empty answers.

The diagnosis (see §3) revealed a three-layer failure whose root cause was that
**BLAST+ was never installed in the Docker image at all** — an oversight from the original
Dockerfile, not caught because the pipeline silently reported success.

### Why the failure was invisible

The `blast_search` harness tool wraps this bash command:

```bash
blastn -db nt -query /workspace/scratch/query.fa -outfmt 6 | tee /workspace/scratch/blast_results.txt
```

When `blastn` is absent (rc=127), `tee` still runs — tee reads from stdin, gets EOF, writes
nothing to file, and exits **rc=0**. The harness sees `rc=0` with empty stdout and calls
`_summarize_blast_output("", ...)`, which emits "No BLAST hits found". There is no trace of
the underlying "command not found" error.

## 3. BLAST failure diagnosis

### Step 1 — Inspect trajectory

hb002 attempt 3 deviated from the others: instead of calling the `blast_search` harness
tool, it used `Bio.Blast.NCBIWWW.qblast()` directly in a Python script inside the
container. The result: **100% identity match to *Bacillus sp. H15-1* (CP018249.1)**.

This proved:
1. The network was fine
2. The 16S sequence matched NCBI entries correctly
3. The harness `blast_search` tool was the only broken piece

### Step 2 — Check the Dockerfile

```dockerfile
# docker/Dockerfile — micromamba install block (before BF-1)
RUN micromamba install -y -n base -c conda-forge -c bioconda \
    samtools=1.19 \
    bcftools=1.19 \
    bedtools=2.31 \
    minimap2 \
    r-base=4.3 \
    ...
```

`blast` was simply absent. The original Dockerfile installed tools for general bioinformatics
but the `blast_search` harness tool (added in the B slice, PR #45) was never followed by a
Dockerfile update to install the binary it wraps.

### Step 3 — Understand the three-layer failure

```
Layer 1: blast never in Dockerfile
         → blastn binary absent from container PATH

Layer 2: blast_search dispatch runs: blastn ... | tee blast_results.txt
         → tee exits rc=0 even when blastn exits rc=127
         → harness sees rc=0 + empty stdout

Layer 3: _summarize_blast_output("") → "No BLAST hits found"
         (before BE fixes: gave no version stamp, so agent couldn't tell if binary ran at all)
         (after BE fixes from RERUN-5: gave "No hits at default parameters. (blastn installed...)"
          with the version clause conditionally omitted when version="" — still misleading)
```

The BE fix (PR #56) improved the message by calling `_get_blast_version()` but only
conditionally included the version clause when the version was non-empty. With no binary,
version=`""` → version clause omitted → the message looked exactly the same as "no network
hits from an installed binary". The distinction was invisible to the agent.

## 4. BF-1: Install BLAST+ in Docker image

**File:** [`docker/Dockerfile`](../../docker/Dockerfile)

Added `blast \` to the micromamba install block:

```dockerfile
RUN micromamba install -y -n base -c conda-forge -c bioconda \
    samtools=1.19 \
    bcftools=1.19 \
    bedtools=2.31 \
    minimap2 \
    blast \          # ← BF-1
    r-base=4.3 \
```

This installs `blastn`, `blastp`, and `blastx` from Bioconda into the base conda
environment. After the image is rebuilt, all three executables are available at
`/opt/conda/bin/` (on `$PATH` due to the `ENV PATH=/opt/conda/bin:$PATH` directive
added in ENV-2).

**Also updated:** `BASH_TOOL` description in [`harness/agent.py`](../../harness/agent.py):

```python
"Pre-installed tools: samtools, bcftools, bedtools, blast (blastn/blastp/blastx), "
"biopython, scanpy, anndata, ..."
```

So the agent no longer needs to guess whether BLAST is available.

> **📦 Bioconda**
> Bioconda is a conda channel specialising in bioinformatics software. The `blast` package
> installs NCBI BLAST+ (Basic Local Alignment Search Tool) and includes `blastn` (nucleotide),
> `blastp` (protein), `blastx` (translated nucleotide query vs protein database), and more.
> BLAST+ supports both local database searches and `-remote` mode (queries NCBI servers directly).
> Further reading: [BLAST+ User Manual](https://www.ncbi.nlm.nih.gov/books/NBK153387/)

## 5. BF-2: Fix silent failure in blast_search dispatch

**File:** [`harness/agent.py`](../../harness/agent.py), `AgentRun._loop()` blast_search branch (~line 444)

### The pre-check

```python
# BF-2: pre-check binary before running so a missing binary is
# never silently reported as "no hits" (the | tee pipe would
# otherwise return rc=0 even when the program is absent).
if program not in self._blast_versions:
    self._blast_versions[program] = _get_blast_version(
        self.container, program
    )
version = self._blast_versions[program]

if not version:
    missing_msg = (
        f"BLAST binary '{program}' not found in the container. "
        f"Install with: micromamba install -c bioconda blast"
    )
    self.logger.log("tool_call", {"blast_command": f"{program} -version (pre-check failed)"})
    self.logger.log("tool_result", {
        "blast_command": missing_msg,
        "summary": missing_msg,
        "returncode": 127,
    })
    result_text = (
        f"BLAST error: {missing_msg}\n\n"
        + _progress_footer(self.steps, self.config.max_steps, self.input_tokens)
    )
    tool_results.append({...})
    continue   # skip running BLAST entirely
```

The `continue` statement jumps back to the top of the tool-dispatch loop without ever
running the `blastn ... | tee` command. The agent sees a clear "not found" message with
an install hint rather than a misleading "No hits".

### `_get_blast_version()` helper

```python
def _get_blast_version(container: Container, program: str) -> str:
    try:
        stdout, _stderr, rc = container.exec_command(f"{program} -version", timeout=5)
    except TimeoutError:
        return ""
    except Exception:
        return ""
    if rc != 0:
        return ""
    first_line = stdout.strip().splitlines()[0] if stdout.strip() else ""
    return first_line
```

Returns the first line of `<program> -version` stdout on success, or `""` on any failure
(non-zero rc, timeout, or exception). The short 5 s timeout prevents this from blocking the
agent loop when the binary is present but the version command hangs.

### Version cache

```python
self._blast_versions: dict[str, str] = {}
```

Added in `AgentRun.__init__`. The version probe runs at most once per (program, container
lifetime) — the result is cached so subsequent calls to `blast_search` with the same program
don't pay the extra `exec_command` overhead.

### pipefail prefix

```python
command = (
    f"set -o pipefail; {program} -db {database} -query {query} "
    f"-outfmt 6 -max_target_seqs {max(max_hits * 2, 50)} "
    f"{remote} {extra} | tee {out_file}"
).strip()
```

`set -o pipefail` changes bash's exit-code semantics so the pipeline's exit code is the
rightmost non-zero exit code, not always `tee`'s exit code. This means: if `blastn` exits
rc=127, the whole pipeline exits rc=127, even though `tee` would exit 0.

The pre-check catches missing binaries before this line, but `set -o pipefail` provides a
defence-in-depth safeguard for scenarios where the pre-check passes but the binary
disappears mid-run (unlikely but possible in theory).

> **📦 bash pipefail**
> In bash, `cmd1 | cmd2` returns the exit code of `cmd2` by default (`$?` = exit code of last command).
> `set -o pipefail` changes this so the pipeline returns the exit code of the first command to fail
> (rightmost non-zero). This is critical when `cmd2` is a simple tee/cat that always exits 0 — without
> pipefail, failures in `cmd1` are silently swallowed. See L-26 in code-learnings for the full rule.

## 6. BF-3: Pre-flight check before eval start

**File:** [`scripts/run_eval.py`](../../scripts/run_eval.py), new function `_preflight_container_tools()` (~line 101)

```python
def _preflight_container_tools(image_name: str) -> None:
    _REQUIRED_TOOLS = [
        ("blastn", "-version", "blast", "micromamba install -c bioconda blast"),
    ]
    console.print("[dim]Checking container tool availability...[/dim]")
    try:
        import docker as docker_sdk
        client = docker_sdk.from_env()
        for binary, flag, pkg_name, install_cmd in _REQUIRED_TOOLS:
            result = client.containers.run(
                image_name,
                command=f"bash -c '{binary} {flag} 2>&1; echo rc=$?'",
                remove=True,
                stdout=True,
                stderr=True,
            )
            output = result.decode() if isinstance(result, bytes) else str(result)
            if "rc=0" not in output:
                console.print(
                    f"[red]Container preflight FAILED: '{binary}' not found...[/red]"
                )
                sys.exit(1)
    except Exception as e:
        console.print(f"[yellow]Container preflight skipped: {e}[/yellow]")
        return
    console.print("[dim]Container tools OK.[/dim]")
```

This function is called from `main()` immediately after `ensure_docker_image()`, before any
benchmark problems are loaded or API calls are made. It starts a throwaway container
(`remove=True`) and runs a one-liner that emits `rc=0` on success or `rc=127` on failure.
Checking for the literal string `"rc=0"` in the output is more robust than checking the
container run's own exit code (which can be confused by docker SDK wrapping).

**Note on single quotes:** The command uses single quotes around the bash -c argument
(`bash -c '...'`) so that `$?` is expanded by the container's bash, not by the host shell
before the string is passed to Docker. If double quotes were used, the host shell would
expand `$?` to `0` before Docker ever saw the string.

**Graceful degradation:** If the Docker SDK is unavailable or the Docker daemon is
unreachable, the check is skipped with a yellow warning. This allows the harness to work
even if `import docker` fails (e.g. in a CI environment without the docker package).

**Smoke test extension:** `scripts/smoke_test_container.py` was also extended:

```python
("blastn -version", "blastn binary installed"),
```

The smoke test provides a second layer of verification (manual, run from the host) that
the newly built image contains the required binary.

## 7. BF-4: Rewrite blast-search SKILL.md + add L-26

### SKILL.md rewrite

**File:** [`SKILLS/blast-search/SKILL.md`](../../SKILLS/blast-search/SKILL.md)

The original GD-5 SKILL.md had a "Critical" section saying BLAST executables are **NOT**
in the container bash PATH. This was accurate when written (BLAST wasn't installed at all),
but after BF-1 installed BLAST the guidance became wrong and potentially confusing.

The rewrite replaces the "NOT in PATH" warning with:

```markdown
## Use blast_search tool — not direct bash

`blastn`, `blastp`, and other BLAST executables are installed at
`/opt/conda/bin/` and available on `$PATH`. However, **always use the
`blast_search` tool call** (not a direct bash invocation) because:

- The tool saves full tabular output to `/workspace/scratch/blast_results.txt`
  and returns only a compact summary, keeping large output out of the context window.
- Piping BLAST output in bash can silently swallow error exit codes.
```

The new guidance is accurate and explains *why* to use the tool call even though the
binary is now on PATH.

### L-26 in code-learnings

**File:** [`.claude/skills/code-learnings/SKILL.md`](../../.claude/skills/code-learnings/SKILL.md)

L-26 was added to document the bash pipeline exit-code swallowing pattern for future agents:

```
## L-26: Bash pipeline exit codes are silently swallowed — always use pipefail or pre-check

Rules:
1. Never pipe harness-dispatched commands without `set -o pipefail`.
2. Pre-check binary availability before running.
3. Any new tool that wraps a binary must add the binary to the Dockerfile.
4. Add a _preflight_container_tools() check to guard eval runs.
```

The lesson also documents the specific incident (RERUN-6, hb002 0/5) and the pattern fix
(from `harness/agent.py` after BF-2).

## 8. End-to-end data flow diagram

### Before BF-2 (broken)

```
AgentRun._loop()
  └─ blast_search tool call
       ├─ _get_blast_version(container, "blastn")
       │    └─ container.exec_command("blastn -version", timeout=5)
       │         → rc=127, stdout=""  [binary missing]
       │    ← returns ""   ← version="" cached
       │
       │  [version="" → no early exit (BF-2 not applied yet)]
       │
       └─ container.exec_command("blastn ... | tee blast_results.txt")
            → blastn: rc=127 (binary not found)
            → tee: rc=0 (reads empty stdin, writes empty file)
            → pipeline overall: rc=0  ← BUG: pipe masks blastn failure
            → stdout=""
       └─ _summarize_blast_output("", program="blastn", version="")
            → "No BLAST hits found."  ← misleading: sounds like network/sequence issue
```

### After BF-2 (fixed)

```
AgentRun._loop()
  └─ blast_search tool call
       ├─ _get_blast_version(container, "blastn")
       │    └─ container.exec_command("blastn -version", timeout=5)
       │         → rc=0, stdout="blastn: 2.16.0+"  [binary present after BF-1 rebuild]
       │    ← returns "blastn: 2.16.0+"  ← cached
       │
       └─ container.exec_command("set -o pipefail; blastn -db nt ... | tee ...")
            → blastn: runs, queries NCBI
            → returns tabular hits or empty output
            → pipeline rc reflects blastn exit code (not tee's)
       └─ _summarize_blast_output(hits, program="blastn", version="blastn: 2.16.0+")
            → compact hit table OR
               "No hits at default parameters. blastn installed (version blastn: 2.16.0+)."
```

### Pre-flight guard (BF-3)

```
scripts/run_eval.py main()
  ├─ parse_args()
  ├─ ensure_docker_image(config.image_name, ...)   [SI hash-gated rebuild]
  ├─ _preflight_container_tools(config.image_name) [BF-3]
  │    └─ docker SDK: run throwaway container
  │         bash -c 'blastn -version 2>&1; echo rc=$?'
  │         ├─ "rc=0" in output → continue
  │         └─ "rc=0" not in output → sys.exit(1) with red error message
  └─ load problems, run eval ...
```

- Was `test_has_bash_path_warning` — checked for "NOT in PATH". Renamed and updated to assert the new guidance: body contains `"blast_search"` and `"tool"`.
