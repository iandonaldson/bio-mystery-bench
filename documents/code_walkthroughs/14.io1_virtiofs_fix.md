## 1. Background and motivation

### What triggered the investigation

During RERUN-6 redux — the benchmark re-run after PR #83 added BLAST+ to the Docker
image — every attempt on problems hb022 and hb053 ended with `resource_abort` within
the first few agent steps. The abort reason was always "Resource deadlock avoided".

A typical failing trajectory looked like:

```
Step 1 — agent runs: ls /workspace/data
Step 1 result: ls: cannot access '/workspace/data/reads.fastq': Resource deadlock avoided
Status: resource_abort
```

This was immediately suspicious: the data files had worked in earlier runs. The Docker
image was freshly rebuilt (forcing a new pull of all layers including the data), and
the host filesystem showed the files were present and correctly sized.

### Why BLAST runs (hb020, recq, hb002) were unaffected

Those problems had already completed before the Docker Desktop session entered its broken
state. hb022 and hb053 ran last — by then VirtioFS was broken.

## 2. Diagnosis — how VirtioFS deadlock manifests

### What VirtioFS is

Docker Desktop on macOS uses **VirtioFS** (a FUSE-based filesystem virtualization layer)
to proxy file operations between the macOS host and the container's Linux VM. Every bind
mount passes through VirtioFS.

### The deadlock state

On long-running Docker Desktop sessions (hours of uptime, many container starts/stops),
VirtioFS can enter a broken state for specific mount points. In this state:

- **File metadata is visible**: `ls -l` shows correct file names and sizes.
- **Data blocks are inaccessible**: any read syscall returns errno 35 (EDEADLK,
  "Resource deadlock avoided").

### The fingerprint

The most reliable early indicator is the block count from `ls -lh`:

```
# Broken VirtioFS mount — total 0 despite non-zero file sizes:
$ ls -lh /workspace/data
total 0
-rw-r--r-- 1 root root 142K May 28 09:00 genome.fasta
-rw-r--r-- 1 root root  12K May 28 09:00 metadata.csv

# Healthy mount (overlay FS) — non-zero block count:
$ ls -lh /workspace/data
total 156K
-rw-r--r-- 1 root root 142K May 28 09:00 genome.fasta
-rw-r--r-- 1 root root  12K May 28 09:00 metadata.csv
```

`total 0` means the kernel reports no allocated blocks — the filesystem is visible but
unreadable. Any attempt to `cat`, `open()`, or `read()` returns EDEADLK.

### Why the scratch mount was immune

The scratch directory (`/workspace/scratch`) is created fresh for each container run
using a new UUID path. VirtioFS's deadlock was mount-point-specific and affected stale
mounts that had been held open across long sessions. A brand-new mount path started in
a healthy state. The data directory was always the same host path (the problem's
extracted data dir), so it stayed broken.

## 3. The fix — `_copy_data_to_container()`

### The principle

Instead of bind-mounting `data_dir` through VirtioFS, stream data files directly into
the container's **overlay FS** via the Docker SDK's `put_archive` method.

The overlay FS lives entirely inside the Docker VM's virtual disk image. It is never
accessed through VirtioFS — reads and writes go through the Linux kernel's native
overlayfs driver inside the VM. This makes it immune to the macOS VirtioFS deadlock.

### The implementation

```python
# harness/container.py

def _copy_data_to_container(self) -> None:
    data_path = Path(self.data_dir)
    buf = io.BytesIO()
    with tarfile.open(fileobj=buf, mode="w") as tar:
        for item in sorted(data_path.iterdir()):
            tar.add(str(item), arcname=item.name)
    buf.seek(0)
    self._container.put_archive("/workspace/data", buf)
```

**Step by step:**

1. **`io.BytesIO()`** — creates an in-memory byte buffer. No temp files are written to
   the host filesystem.

2. **`tarfile.open(fileobj=buf, mode="w")`** — writes a tar archive into the buffer.
   `arcname=item.name` strips the host path prefix so the archive contains just
   `reads.fastq`, not `/Users/ian/.../reads.fastq`.

3. **`sorted(data_path.iterdir())`** — deterministic order for reproducibility.

4. **`buf.seek(0)`** — rewind before reading. Required because `tarfile.open` writes
   forward through the buffer; without the seek, `put_archive` reads 0 bytes.

5. **`put_archive("/workspace/data", buf)`** — Docker SDK method. The daemon receives
   the tar stream and extracts it at the specified destination path inside the container.
   Docker creates `/workspace/data/` if it does not exist. The files land in the
   container's overlay FS layer, never touching VirtioFS.

> **📦 Docker `put_archive`**
> `Container.put_archive(path, data)` extracts a tar archive into `path` inside the
> running container. The `data` argument can be a file-like object or raw bytes.
> The destination directory is created automatically. This is the same mechanism
> `docker cp` uses under the hood, but called directly from Python without spawning
> a subprocess.

### What changed in `start()`

Before IO-1, `start()` built a `volumes` dict with two entries:

```python
# BEFORE (bind-mounts both scratch and data):
volumes = {
    str(scratch_dir): {"bind": "/workspace/scratch", "mode": "rw"},
    str(self.data_dir): {"bind": "/workspace/data",  "mode": "ro"},
}
```

After IO-1, only the scratch mount remains in `volumes`; data files are injected
after the container starts:

```python
# AFTER (only scratch is bind-mounted; data goes via overlay FS):
volumes = {str(scratch_dir): {"bind": "/workspace/scratch", "mode": "rw"}}
self._container = self._client.containers.run(
    self.image, ..., volumes=volumes,
)
if self.data_dir and Path(self.data_dir).exists():
    self._copy_data_to_container()
```

## 4. Updated `start()` flow

```
Container.start()
│
├── scratch_dir = Path(".scratch").resolve() / self.name
├── scratch_dir.mkdir(parents=True, exist_ok=True)
├── volumes = {str(scratch_dir): {"bind": "/workspace/scratch", "mode": "rw"}}
│
├── self._container = client.containers.run(
│       image, detach=True, remove=True,
│       mem_limit=..., nano_cpus=...,
│       network_mode="bridge",
│       volumes=volumes          ← scratch only
│   )
│
└── if self.data_dir and Path(self.data_dir).exists():
        self._copy_data_to_container()
            ├── build tar archive in io.BytesIO()
            └── self._container.put_archive("/workspace/data", buf)
                    └── Docker daemon writes to container overlay FS
                        (immune to VirtioFS)
```

## 5. End-to-end data flow diagram

```
Host filesystem                Docker VM
──────────────                 ─────────────────────────────────────────
.scratch/<run-id>/  ─── bind mount (VirtioFS) ──▶  /workspace/scratch/
                                                     (agent writes here)

data_dir/           ─── tar stream (put_archive) ─▶ container overlay FS
  reads.fastq            (bypasses VirtioFS)         /workspace/data/
  metadata.csv                                          reads.fastq
                                                        metadata.csv
```

The scratch mount still uses VirtioFS because:
1. It must be readable from the host (artifact collection copies it to `artifacts_dir`).
2. Each run creates a **fresh** UUID path — VirtioFS deadlocks only affect stale,
   long-held mount points.

## 9. Glossary

| Term | Definition |
|------|-----------|
| VirtioFS | macOS Docker Desktop filesystem virtualization layer; proxies file operations between the macOS host and the Linux VM via a FUSE-based protocol |
| EDEADLK | errno 35, "Resource deadlock avoided" — the kernel error returned when VirtioFS enters a broken state |
| Overlay FS | Linux kernel filesystem (`overlayfs`) used by Docker to implement container layers; lives inside the Docker VM's virtual disk, immune to VirtioFS |
| `put_archive` | Docker SDK method to extract a tar archive directly into a container path, bypassing VirtioFS |
| Bind mount | A host directory made available inside a container; passes through VirtioFS on macOS |
