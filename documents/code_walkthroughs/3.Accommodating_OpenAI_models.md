## 1. Background: What "Accommodating" Means

Walkthrough #2 described how `AnthropicProvider` and `OpenAIProvider` were built to
give any OpenAI-compatible model access to the bash tool and full ReACT
(Reasoning + Acting) loop. After connecting Cerebras (running Qwen3-235B), two
classes of problem appeared:

**Behavioural problems** — the model ran correctly but produced wrong or
hard-to-score answers:
- Models called tools without explaining why, making trajectories hard to audit
- Models installed already-present packages, wasting steps
- Models matched the logic of a rubric answer but formatted it differently
  (e.g. `Sample01` vs `Sample_01`), failing exact-match scoring
- Models made unverified assumptions about gene regulatory direction

**Infrastructure problems** — the critic/judge components broke when the agent
used a non-Anthropic provider:
- The critic used the wrong API endpoint (Cerebras instead of Anthropic)
- The judge had the same cross-provider routing bug
- The Haiku model string was deprecated, causing 404s
- `cache_control` blocks were sent on empty system prompts, causing 400s

This walkthrough covers all fixes in both categories.

> **📦 ReACT (Reasoning + Acting)**
> ReACT is an agentic design pattern where the model alternates between
> *reasoning* (writing text about what to do next) and *acting* (calling a
> tool). The reasoning is not just for the human reader — it conditions the
> model's next generation. Requiring explicit narration before every tool call
> enforces this pattern even for models that would otherwise skip the reasoning
> step and jump straight to tool calls.
> Further reading: [ReACT paper (Yao et al. 2023)](https://arxiv.org/abs/2210.03629)

## 2. Narration Requirement — `prompts/system.txt`

**File:** [prompts/system.txt](../../prompts/system.txt)

### 2.1 Why narration matters for non-Anthropic models

Claude models (especially Sonnet and Opus) tend to naturally write reasoning text
before tool calls. Many OpenAI-compatible models — Llama, Qwen, Phi — do not.
They often jump directly to a tool call with no preceding text, producing
trajectories like:

```
[assistant]
<tool_use: bash>{"command": "head -20 /workspace/data/counts.csv"}
```

This is a problem for three reasons:

1. **Trajectory quality**: The Markdown trajectory viewer (`trajectory_to_md.py`)
   shows the `reasoning` field from each assistant turn. Empty reasoning makes the
   trajectory unreadable — you cannot tell what the model "thought" it was doing.

2. **LLM judge accuracy**: The critic agent (§5) formats the trajectory for a
   second model that audits the reasoning. With no reasoning text, the critic has
   nothing to audit.

3. **Model behaviour**: Forcing a brief narration before each tool call acts as a
   lightweight chain-of-thought that measurably improves accuracy on reasoning
   tasks, because the text conditions the model's subsequent generation.

The fix is a system prompt rule that applies to all providers.

### 2.2 The narration rule

```
# prompts/system.txt  (added in PR #22)

## Narration

Before EVERY tool call, write 1–2 sentences in your response explaining:
(a) what you are about to do, and (b) why it will help solve the problem.
Never call a tool without this brief narration first.
```

This rule is:
- **Universal** (applies regardless of provider — the system prompt is
  passed identically to both `AnthropicProvider` and `OpenAIProvider`)
- **Minimal** (1–2 sentences — enough for auditing, not so much that it wastes
  tokens in the context window)
- **Absolute** ("Never call a tool without...") — necessary for models that
  would otherwise skip narration unless forbidden

> **📦 Chain-of-thought (CoT) prompting**
> Chain-of-thought prompting asks the model to write out its reasoning step by
> step before giving an answer. "Let me explain before I act" is a
> single-step CoT applied to tool use. Even a single sentence of narration
> has been shown to improve performance over silent tool dispatch, because the
> generated text about the plan conditions the model's choice of arguments.
> Further reading: [Chain-of-Thought Prompting (Wei et al. 2022)](https://arxiv.org/abs/2201.11903)

## 3. Prompt Engineering Additions — `prompts/system.txt`

**File:** [prompts/system.txt](../../prompts/system.txt)

Three further rules were added to the system prompt based on observed failure modes
from benchmark runs.

### 3.1 Which-before-install rule (PR #23)

**Failure mode:** Models would run `pip install pandas` or
`micromamba install samtools` as their first action, even though these packages
are pre-installed in the Docker image. This wastes 1–3 steps and can introduce
version conflicts.

```
# prompts/system.txt

Before installing any tool, verify it is not already available:
```bash
which python3 python bedtools samtools bwa bowtie2 minimap2 salmon kallisto
```
Never attempt installation as a first step — most bioinformatics tools are
pre-installed.
```

The `which` command exits with code 0 if the binary exists and 1 if not,
giving the model a quick and reliable check with a single tool call.

### 3.2 Answer format matching (PR #24)

**Failure mode:** Models got the right *logical* answer but formatted it
differently from the rubric, causing exact-match scoring to fail. Example:
the rubric says `Sample_01` (with underscore), but the model outputs `Sample01`
because the question text uses an inconsistent convention.

```
# prompts/system.txt  (added to "General approach" §7)

Your answer must match exactly the syntax and formatting used in the question
and its starting materials. For example: if sample names appear as `Sample_01`
in the data, use `Sample_01` — not `Sample01`, `sample_01`, or `SAMPLE_01`.
If the question specifies a particular format (e.g. binomial nomenclature,
a unit, a list style), follow it precisely. The scorer is exact-match;
formatting errors count as wrong.
```

This rule points the model to the *data files* as the authoritative source of
formatting, which is the same source the rubric answer was derived from.

### 3.3 Assumption-checking rules (PR #25)

**Failure mode:** Models made implicit assumptions about gene regulatory
direction or dataset completeness, then gave confident but wrong answers.

Two specific patterns were generalised from observed benchmark failures:

```
# prompts/system.txt  (inside "General approach" §6)

Before stating your final answer, explicitly check any assumptions your
analysis depends on. In particular:
- When grouping samples using a gene signature score, verify the expected
  direction of regulation for each gene in that condition. Genes in a pathway
  signature are not always upregulated — e.g. a ferroptosis inducer may suppress
  protective genes (GPX4) rather than activate them.
- When inferring a condition from sequence homology (BLAST), check that the
  top-hit annotations consistently reflect the experimental condition, not just
  species or tissue of origin.
- When the problem provides multiple items to analyse (sequences, genes, samples,
  peaks), analyse ALL of them — not just the first few. Sampling only the first
  3 of 18 genes, for example, introduces bias and can produce a completely wrong
  conclusion if the remaining items tell a different story.
- State what you assumed and confirm it with data before drawing your conclusion.
```

> **📦 Gene signature scoring and directionality**
> A gene signature is a list of genes whose combined expression discriminates
> between two biological conditions. Scoring algorithms (e.g. ssGSEA, AUCell)
> assign a score per sample based on whether the signature genes are
> up- or down-regulated. The critical subtlety: a *protective* gene like GPX4
> (which prevents ferroptotic cell death) will be *low* in cells that are
> ferroptosis-susceptible, even though it belongs to the "ferroptosis pathway"
> signature. A model that assumes all signature genes are upregulated will
> rank samples in the wrong order.
> Further reading: [ssGSEA (Barbie et al. 2009)](https://www.nature.com/articles/nature08460)

## 4. Critic Prototype Script — `scripts/critic_prototype.py`

**File:** [scripts/critic_prototype.py](../../scripts/critic_prototype.py)
*(Added in PR #25 — standalone validation tool)*

Before wiring a critic into the main harness loop, it was validated as a
standalone script that reads a completed trajectory JSONL and asks Claude Haiku
to identify unverified assumptions.

```python
# scripts/critic_prototype.py  (key section)
def format_trajectory(jsonl_path: str) -> str:
    """Load a trajectory JSONL and format it for the critic."""
    sections = []
    with open(jsonl_path) as f:
        for line in f:
            event = json.loads(line)
            role = event.get("role", "")
            data = event.get("data", {})
            if role == "user":
                sections.append(f"PROBLEM:\n{data.get('question', '')[:2000]}")
            elif role == "assistant":
                if reasoning := data.get("reasoning", "").strip():
                    sections.append(f"AGENT REASONING:\n{reasoning[:400]}")
            elif role == "tool_call":
                sections.append(f"BASH COMMAND:\n{data.get('command', '')}")
            elif role == "tool_result":
                sections.append(f"TOOL OUTPUT:\n{data.get('stdout', '')[:600]}")
            elif role == "status":
                sections.append(f"FINAL ANSWER:\n{data.get('final_message', '')}")
    return "\n\n---\n\n".join(sections)
```

The prototype was validated on two known-difficult problems before PR #26
integrated the same logic into `AgentRun`. The standalone script remains useful
for auditing any saved trajectory without running the full harness:

```bash
python scripts/critic_prototype.py results/trajectories/problem-hb022_attempt-0.jsonl
```

## 5. Critic Agent Architecture — `harness/agent.py`

**File:** [harness/agent.py](../../harness/agent.py)
*(Added in PR #26; routing fixed in PRs #28, #31)*

The critic is an optional second LLM call made after the agent reaches its final
answer. It audits the trajectory for unverified assumptions and, if it finds
high-risk ones, injects a correction prompt to give the agent one more chance
to verify before committing.

```
Normal run (no critic):
  agent → [tool calls] → FINAL ANSWER → score

Run with critic (--critic-injection-points after_final_answer):
  agent → [tool calls] → FINAL ANSWER
                              ↓
                       critic audits trajectory
                              ↓
                  [if HIGH-risk assumptions found]
                              ↓
             critic feedback injected as user message
                              ↓
                   agent verifies + revised FINAL ANSWER
                              ↓
                           score
```

### 5.1 CRITIC_SYSTEM_PROMPT constant

```python
# harness/agent.py

CRITIC_SYSTEM_PROMPT = """\
You are a scientific reasoning auditor reviewing an AI agent's solution to a
computational biology problem. Your job is to identify assumptions the agent
made that were NOT empirically verified during the analysis.

For each unverified assumption:
1. State the assumption clearly
2. Explain what the agent would need to do to verify it
3. Rate the risk: HIGH (would likely change the conclusion if wrong),
   MEDIUM (might affect confidence but not conclusion), or LOW (minor)

Be concrete and specific — cite the actual reasoning steps where the assumption
was made. Do not flag assumptions that were explicitly tested.
Focus on the 2-3 most consequential unverified assumptions.

At the end, state whether any HIGH-risk assumption would plausibly change the
final answer if it turned out to be wrong.\
"""
```

The three-tier risk rating (HIGH / MEDIUM / LOW) is important: `_format_critic_injection`
only asks the agent to address HIGH-risk concerns (§5.7). MEDIUM and LOW concerns
are included in the audit text for the human reviewer but do not trigger additional
tool calls by the agent, keeping token costs bounded.

### 5.2 RunConfig additions — `harness/config.py`

**File:** [harness/config.py](../../harness/config.py)

```python
# harness/config.py
@dataclass
class RunConfig:
    ...
    critic_injection_points: list[str] = field(default_factory=list)
    # Named points in the agent loop where critic fires.
    # Currently only "after_final_answer" is implemented.
    # Empty list (default) = critic disabled.

    critic_model: str = ""
    # Model name for the critic. Empty string = use same model as agent.
    # Example: "claude-haiku-4-5-20251001" when agent is on Cerebras.
```

Both fields default to "off" states (`[]` and `""`), so existing code that
constructs `RunConfig` without these fields is unaffected.

### 5.3 `AgentRun.__init__`: accepting `critic_client`

```python
# harness/agent.py
class AgentRun:
    def __init__(
        self,
        client: Provider,
        ...
        critic_client: Provider | None = None,   # ← new (PR #28)
    ):
        self.client = client
        self.critic_client = critic_client or client
        # If no separate critic client is passed, fall back to the agent client.
        # This handles the same-provider case (agent=Anthropic, critic=Haiku)
        # without needing special-case logic in run_eval.py.
```

The `or client` fallback means the critic parameter is always populated at
`__init__` time — `_run_critic` never needs to check for `None`.

> **⚠ Bug history (L-01 from `SKILLS/code-learnings/SKILL.md`)**
> PR #26 added `critic_client` as a constructor argument but `_run_critic()`
> still called `self.client.chat()` (the agent's client). PR #28 fixed the
> *run_eval.py* side (building the separate client) but missed updating the
> call site inside `_run_critic`. PR #31 finally fixed the call site.
> The lesson: any time a new `*_client` attribute is added, grep immediately
> for every method that makes LLM calls and confirm it uses the right attribute.

### 5.4 `_loop`: critic injection point

```python
# harness/agent.py  (_loop, after stop_reason == "end_turn")

if response.stop_reason == "end_turn":
    # Critic injection point: after_final_answer
    if (
        "after_final_answer" in self.config.critic_injection_points
        and not self._critic_injected   # ← fire at most once per run
    ):
        self._critic_injected = True
        critique = self._run_critic(response.text)
        if critique:
            self.logger.log("critic", {
                "model": self.config.critic_model or self.config.model,
                "critique": critique,
            })
            self.messages.append({
                "role": "user",
                "content": _format_critic_injection(critique),
            })
            continue   # ← re-enter the loop; agent responds to the critique

    # No critic (or critic already fired): finalize
    self.logger.log("status", {"status": "success", ...})
    return AgentResult(status="success", ...)
```

The `_critic_injected` flag prevents infinite loops if the agent's response to
the critique itself looks like a final answer — the critic fires exactly once
per run. The `continue` statement re-enters the `while True` loop, so the agent
can make further bash calls (to verify assumptions flagged by the critic) before
giving its revised final answer.

### 5.5 `_run_critic`: calling the critic model

```python
# harness/agent.py

def _run_critic(self, final_answer: str) -> str:
    """Call the critic model on the current trajectory. Returns critique text, or '' on error."""
    trajectory_text = self._format_trajectory_for_critic(final_answer)
    critic_model = self.config.critic_model or self.config.model
    try:
        response = self.critic_client.chat(   # ← uses critic_client, NOT self.client
            model=critic_model,
            system=CRITIC_SYSTEM_PROMPT,
            messages=[{
                "role": "user",
                "content": f"Please audit the following agent trajectory:\n\n{trajectory_text}",
            }],
            tools=[],   # critic never uses tools
            max_tokens=1024,
        )
        # Attribute critic token usage to this run's totals
        self.cost_tracker.add(
            response.usage.input_tokens,
            response.usage.output_tokens,
            response.usage.cache_read_tokens,
        )
        self.input_tokens += response.usage.input_tokens
        self.output_tokens += response.usage.output_tokens
        self.cache_read_tokens += response.usage.cache_read_tokens
        return response.text
    except Exception as e:
        self.logger.log("critic_error", {"error": str(e), "critic_model": critic_model})
        return ""   # ← return empty string on error; agent continues without critique
```

Key design decisions:
- **`tools=[]`**: the critic is a pure text task; no bash access
- **`max_tokens=1024`**: enough for 2-3 structured assumption analyses
- **Cost attribution**: critic tokens are added to `self.cost_tracker` so the
  per-run `cost_usd` in `scores.json` reflects the total cost including the critique
- **Error logging**: exceptions are logged as `critic_error` in the trajectory
  (not silently swallowed) — see L-02 in `SKILLS/code-learnings/SKILL.md`

### 5.6 `_format_trajectory_for_critic`: building the audit text

```python
# harness/agent.py

def _format_trajectory_for_critic(self, final_answer: str) -> str:
    """Render self.messages as readable text for the critic."""
    sections = []
    first_user = True
    for msg in self.messages:
        role = msg.get("role", "")
        content = msg.get("content", [])
        ...
        if role == "user":
            for block in content:
                if btype == "text" and first_user:
                    first_user = False
                    sections.append(f"PROBLEM:\n{block.get('text','')[:3000]}")
                elif btype == "tool_result":
                    result = block.get("content", "")
                    sections.append(f"TOOL RESULT:\n{str(result)[:600]}")
        elif role == "assistant":
            for block in content:
                if btype == "text":
                    text = block.get("text", "").strip()
                    if text:
                        sections.append(f"AGENT REASONING:\n{text[:400]}")
                elif btype == "tool_use":
                    cmd = block.get("input", {}).get("command", "")
                    sections.append(f"BASH COMMAND:\n{cmd[:25 lines]}")
    sections.append(f"FINAL ANSWER:\n{final_answer}")
    return "\n\n---\n\n".join(sections)
```

Character limits per section (3000 / 600 / 400) keep the critic's input
under ~8000 tokens for a typical 15-step run. The `first_user` flag skips
the resource snapshot at the top of the first user message — the critic
doesn't need to know the container's RAM and disk numbers.

### 5.7 `_format_critic_injection`: the feedback message to the agent

```python
# harness/agent.py

def _format_critic_injection(critique: str) -> str:
    return (
        "[CRITIC REVIEW]\n"
        "A scientific reasoning auditor has reviewed your analysis and identified "
        "the following concerns:\n\n"
        f"{critique}\n\n"
        "Please address any HIGH-risk concerns before finalising your answer:\n"
        "- If you agree with a concern, use bash to verify the assumption, then state "
        "your revised FINAL ANSWER.\n"
        "- If you disagree, briefly explain why and restate your original FINAL ANSWER.\n"
        "You must end with: FINAL ANSWER: <answer>"
    )
```

The `[CRITIC REVIEW]` prefix makes the injection visually distinct in the
Markdown trajectory. The agent is given a binary choice: verify with bash, or
disagree and defend. Either path must end with a `FINAL ANSWER:` line so the
`extract_final_answer()` function in `scorer.py` can parse the response.

## 6. Cross-Provider Client Routing — `scripts/run_eval.py`

**File:** [scripts/run_eval.py](../../scripts/run_eval.py)
*(PRs #28, #30, #32)*

### 6.1 Why a separate critic client is needed

When the agent runs on Cerebras (`--provider openai --api-base-url https://api.cerebras.ai/v1`)
and the critic/judge uses Claude Haiku, there are two distinct API endpoints that
need to be called. Before PR #28, both calls went through `self.client` — the
Cerebras `OpenAIProvider`. The Cerebras endpoint does not recognise
`claude-haiku-4-5-20251001` as a valid model name and returns an error.

The fix: detect that the critic model starts with `"claude-"` while the agent
provider is not `"anthropic"`, and build a separate `AnthropicProvider` for
critic/judge calls.

### 6.2 Building `critic_client` in `main()`

```python
# scripts/run_eval.py  (inside main(), after client is built)

critic_client = None
if critic_injection_points:
    resolved_critic = critic_model or model
    if resolved_critic.startswith("claude-") and provider != "anthropic":
        # Cross-provider: critic is Claude but agent is on Groq/Cerebras/etc.
        anthropic_key = os.environ.get("ANTHROPIC_API_KEY", "")
        critic_client = build_provider("anthropic", anthropic_key, None, resolved_critic)
    else:
        critic_client = client  # same provider; model routing handled inside AgentRun
```

The guard `resolved_critic.startswith("claude-")` is intentionally simple —
it catches the common case (Haiku as critic for non-Anthropic agents). For
non-Claude critic models on other providers, `critic_client = client` falls
through and uses the agent's provider, which is correct.

### 6.3 Building `judge_client` in `main()`

The LLM-as-judge scorer has the same cross-provider routing need. It was fixed
in PR #30 using the same pattern:

```python
# scripts/run_eval.py  (inside main())

# Build judge client — may differ from agent client
resolved_judge = judge_model or ("claude-haiku-4-5-20251001" if provider == "anthropic" else model)
if resolved_judge.startswith("claude-") and provider != "anthropic":
    anthropic_key = os.environ.get("ANTHROPIC_API_KEY", "")
    judge_client = build_provider("anthropic", anthropic_key, None, resolved_judge)
else:
    judge_client = client
    judge_client.judge_model = resolved_judge
```

> **Design note:** `judge_client` is not passed to `AgentRun` — the agent loop
> does not call the judge. Instead `judge_client` is passed directly to
> `score_answer()` in the per-problem scoring loop (§6.4). This keeps the
> routing concern in `run_eval.py`, not spread across multiple harness modules.

### 6.4 Passing `judge_client` to `score_answer`

```python
# scripts/run_eval.py  (_run_problem)

correct = score_answer(predicted, problem.answer_rubric, client=judge_client)
```

Before this fix, `client` (the agent's Cerebras provider) was passed here.
The scorer's `_llm_judge` would try to call `client.chat(model="claude-haiku-...")`,
which Cerebras would reject. Now `judge_client` is the correctly-routed Anthropic
provider.

## 7. LLM Judge Hardening — `harness/scorer.py`

**File:** [harness/scorer.py](../../harness/scorer.py)
*(PR #29)*

Two defensive improvements were made to `_llm_judge` and the answer extraction
pipeline.

### 7.1 Rubric fast-path extraction

Some rubric strings have the format: `"The answer is CTCF. Score 1.0 if..."`.
Before PR #29, these always went through the LLM judge even when the predicted
answer exactly matched the stated answer. The LLM judge is unreliable under
load and was incorrectly scoring `CTCF == CTCF` as NO.

```python
# harness/scorer.py

def _extract_rubric_answer(rubric: str) -> str | None:
    """Pull the literal answer out of 'The answer is X. Score ...' rubrics."""
    m = re.search(r"(?i)the answer is\s+(.+?)(?=\s+Score\b)", rubric)
    return m.group(1).strip() if m else None
```

```python
# harness/scorer.py  (score_answer, before _llm_judge is called)

rubric_answer = _extract_rubric_answer(rubric)
if rubric_answer and predicted.strip().lower() == rubric_answer.lower():
    return True   # fast-path: skip LLM call entirely
```

The regex `(?=\s+Score\b)` is a lookahead — it matches up to but not including
the ` Score` clause, preventing `"CTCF Score 1.0 if..."` from being captured
as the answer text.

> **📦 Lookahead assertion in regular expressions**
> `(?=...)` is a *zero-width lookahead* — it asserts that the pattern inside
> must be present at the current position, but does not consume any characters.
> This means the match of the outer group stops precisely where the lookahead
> begins, giving a clean boundary without needing to split on a fixed delimiter.
> Further reading: [Python `re` module — lookahead assertions](https://docs.python.org/3/library/re.html#regular-expression-syntax)

### 7.2 Empty-prediction guard

```python
# harness/scorer.py  (_llm_judge)

def _llm_judge(predicted: str, rubric: str, client: Any) -> bool:
    if not predicted or not predicted.strip():
        return False   # ← guard: no LLM call for empty predictions
    ...
```

Without this guard, an empty `predicted` string would go to the LLM judge,
which would inconsistently return YES or NO for "did the model answer nothing?".
Now it immediately returns `False`.

### 7.3 List normalisation step (PR #53)

**Failure mode (hb022):** The upstream HuggingFace rubric for hb022 is malformed.
The intended rubric answer is the Python list `['Sample_01', 'Sample_02', ..., 'Sample_08']`,
but the opening `['` was stripped when the dataset was built, leaving:

```
The answer is: Sample_01', 'Sample_02', ..., 'Sample_08' Score 1.0 ...
```

The question instructs the model to use bracket format (`[Sample_01, Sample_02, ...]`),
so models consistently predict `[Sample_01, ..., Sample_08]`. Neither the exact-match
step nor the rubric fast-path (§7.1) handles the format difference, and the LLM judge
also fails to recognise the two formats as equivalent — scoring every correct attempt
as wrong.

The fix adds two functions and a new step 3 in `score_answer`:

```python
# harness/scorer.py

def _normalize_list(text: str) -> Optional[list[str]]:
    """Parse a comma-separated identifier list, tolerant of brackets and quotes.

    Accepts: [A, B, C]  |  'A', 'B', 'C'  |  A', 'B', 'C  (malformed leading quote)
    Returns sorted list of non-empty items, or None if fewer than 2 items found.
    """
    cleaned = text.strip().strip("[]").replace("'", "").replace('"', "")
    items = [item.strip() for item in cleaned.split(",")]
    items = [item for item in items if item and item != "..."]
    return sorted(items) if len(items) >= 2 else None


def _list_match(predicted: str, rubric: str) -> Optional[bool]:
    """Return True/False/None for list-typed answers.

    True  — both parse as lists and contain the same identifiers
    False — both parse as same-length lists but items differ
    None  — can't determine (not list-shaped, or different lengths)
    """
    rubric_answer = _extract_rubric_answer(rubric) or rubric
    pred_list = _normalize_list(predicted)
    rub_list = _normalize_list(rubric_answer)
    if pred_list is None or rub_list is None:
        return None
    if pred_list == rub_list:
        return True
    if len(pred_list) == len(rub_list):
        return False
    return None
```

`_normalize_list` strips brackets and quotes, splits by comma, filters out bare
ellipsis tokens (`...`), and returns a sorted list. The sort ensures that
`[B, A, C]` and `[A, B, C]` compare equal — useful for problems where sample
ordering is arbitrary.

`_list_match` delegates rubric-answer extraction to `_extract_rubric_answer`
(reusing the existing regex), normalises both sides, then returns a typed result:

| Return | Meaning | Action in `score_answer` |
|--------|---------|--------------------------|
| `True` | Identical identifier sets | Return `True` — correct, no LLM call |
| `False` | Same-length lists, different items | Fall through to LLM judge |
| `None` | Not parseable as lists, or different lengths | Fall through to LLM judge |

Only `True` short-circuits the pipeline. This is conservative: if the list
structure is ambiguous or wrong, the LLM judge still gets a chance to adjudicate.

> **Why not fix the rubric upstream?**  
> The rubric lives in the HuggingFace dataset (`Anthropic/BioMysteryBench-preview`).
> Patching a dataset record requires a new dataset commit and users pulling a new
> revision. The scorer fix is local, testable, and handles the same class of
> format mismatch for any future problem where rubric and prediction use different
> list syntax.

### 7.4 Full `score_answer` pipeline

After all three PRs, the scoring pipeline in `score_answer` has four steps:

```python
# harness/scorer.py

def score_answer(predicted: str, rubric: str, client: Optional[Any] = None) -> bool:
    # 1. Exact match (case-insensitive, stripped)
    if _exact_match(predicted, rubric):
        return True

    # 2. Numeric tolerance (±5% or ±0.1 absolute)
    numeric_result = _numeric_match(predicted, rubric)
    if numeric_result is not None:
        return numeric_result

    # 3. List normalisation — handles bracket/quote format mismatches (e.g. hb022)
    list_result = _list_match(predicted, rubric)
    if list_result is True:
        return True

    # 4. LLM-as-judge fallback (requires API client)
    if client is not None:
        return _llm_judge(predicted, rubric, client)

    return False
```

Steps 1–3 are deterministic and require no API call. Step 4 (LLM judge) is
only reached for answers that do not match any structural pattern — typically
free-text biological names or entities where semantic equivalence must be
assessed (e.g. "HSP70" vs "heat shock protein 70").

## 8. Preflight Model Ping — `scripts/run_eval.py`

**File:** [scripts/run_eval.py](../../scripts/run_eval.py)
*(PR #32)*

### 8.1 `_ping_model()`

Before PR #32, a misconfigured model name (wrong string, deprecated model,
wrong provider endpoint) would only surface after Docker started and the first
problem began — potentially 30–60 seconds into the run.

```python
# scripts/run_eval.py

def _ping_model(client: "Provider", model: str, label: str) -> None:
    """Make a minimal 1-token API call to verify the model endpoint is reachable."""
    try:
        client.chat(
            model=model,
            system="",
            messages=[{"role": "user", "content": [{"type": "text", "text": "ping"}]}],
            tools=[],
            max_tokens=1,
        )
        console.print(f"  [green]✓ {label} ({model}) reachable[/green]")
    except Exception as e:
        console.print(f"  [red]✗ {label} ({model}) failed: {e}[/red]")
        console.print("[red]Aborting: fix the model name or API key before running.[/red]")
        sys.exit(1)
```

`max_tokens=1` requests a single token response, minimising cost (~$0.000001)
while still verifying that the endpoint accepts the model name and API key.

### 8.2 Where pings are called

```python
# scripts/run_eval.py  (inside main(), after all clients are built, before Docker check)

seen_clients: set[int] = set()   # track by object id to avoid pinging the same client twice

_ping_model(client, model, "agent")
seen_clients.add(id(client))

if judge_client and id(judge_client) not in seen_clients:
    _ping_model(judge_client, resolved_judge, "judge")
    seen_clients.add(id(judge_client))

if critic_client and id(critic_client) not in seen_clients:
    resolved_critic_model = critic_model or model
    if resolved_critic_model:
        _ping_model(critic_client, resolved_critic_model, "critic")
        seen_clients.add(id(critic_client))
```

The `id(client)` deduplication prevents pinging the same `(endpoint, model)`
combination twice in same-provider setups (e.g. agent and judge both on
Anthropic with Haiku). `id()` is the object identity in CPython — reliable
for deduplication within a single run.

## 9. API Hardening — `harness/llm.py`

**File:** [harness/llm.py](../../harness/llm.py)
*(PR #33)*

### 9.1 cache_control guard on empty system prompt

`AnthropicProvider.chat()` originally always wrapped the system prompt in a
`cache_control: ephemeral` block:

```python
# harness/llm.py  (BEFORE PR #33 — buggy)
system_with_cache = [
    {"type": "text", "text": system, "cache_control": {"type": "ephemeral"}}
]
response = self._client.messages.create(
    ...
    system=system_with_cache,
    ...
)
```

When `system=""` (which happens when `AnthropicProvider` is used as the critic
or judge client, since those calls pass an empty string for system in some
code paths), the Anthropic API returns:

```
400 invalid_request_error: cache_control cannot be set for empty text blocks
```

The fix guards on `system` being non-empty:

```python
# harness/llm.py  (AFTER PR #33 — correct)
kwargs: dict[str, Any] = dict(
    model=model,
    max_tokens=max_tokens,
    messages=messages,
    tools=tools if tools else [],
)
if system:   # ← only add system kwarg when non-empty
    kwargs["system"] = [
        {"type": "text", "text": system, "cache_control": {"type": "ephemeral"}}
    ]
response = self._client.messages.create(**kwargs)
```

> **📦 Anthropic `cache_control` rules**
> The Anthropic API requires that any text block marked with
> `cache_control: {"type": "ephemeral"}` contains at least some text. An empty
> `text: ""` with a `cache_control` key is rejected with a 400 error. This
> constraint does not appear in the API reference documentation; it is only
> discoverable by hitting the error. The guard `if system:` prevents the block
> from being added at all when the system prompt is empty.
