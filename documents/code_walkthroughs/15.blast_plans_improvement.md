## 1. Background

### What RERUN-6-redux revealed

After BF-1..4 (PR #83) installed BLAST+ in the Docker image and fixed the silent `rc=0`
swallowing bug, hb002 improved from 0/5 to 2/5. The 3 remaining failures shared a common
failure mode: the agent received BLAST output that said "No hits" but the real reason was a
timeout or network error — not a genuine absence of matching sequences.

Three new problems were identified:

**Problem 1 — rc mis-mapping.** When `_summarize_blast_output` received empty stdout, it
unconditionally returned "No hits at default parameters — consider (a) -evalue 1 (b)
blastn-short …". It had no awareness of *why* the output was empty. A timeout (`rc=-1`), a
transient network failure (`rc=5`), and a rate-limit error (`rc=255`) all looked identical
to a genuine no-hits result. The agent then tried relaxing E-value or switching program —
irrelevant actions when the real fix was to trim the query or retry.

**Problem 2 — Taxid hallucination.** The hit table previously showed only the NCBI
accession ID (e.g. `CP018249.1`). To map this to a species name the agent had to recall from
training memory — which it sometimes got wrong. The fix was to request `sscinames` as a
custom field in the BLAST tabular output format so the species name arrives directly in the
result.

**Problem 3 — No rate-limit enforcement.** NCBI's API guidelines allow at most 3 remote
BLAST calls per second. The harness made no attempt to pace calls, risking `rc=255` errors
during any run that issued several BLAST searches in quick succession.

## 2. BP-1 — rc-specific BLAST diagnostics

### New constant: `_BLAST_RC_MESSAGES`

**File:** [`harness/agent.py`](../../harness/agent.py)

A module-level dict maps every official BLAST+ exit code to a plain-English diagnostic
the agent can act on:

```python
_BLAST_RC_MESSAGES: dict[int, str] = {
    -1:  "Timed out — query too large or network stall. Use ≤1500 bp for remote BLAST.",
    1:   "Invalid query or options — check FASTA format and flags.",
    2:   "Database error — NCBI nt/nr may be temporarily unavailable.",
    3:   "BLAST engine error — retry with shorter query.",
    4:   "Out of memory — use shorter query.",
    5:   "Network error connecting to NCBI — transient failure, retry. Not 'no hits'.",
    6:   "Output file error — check write permissions.",
    127: "Binary not found — install with: micromamba install -c bioconda blast",
    255: "Rate-limited or unknown NCBI error — back off and retry. Not 'no hits'.",
}
```

> **📦 BLAST+ exit codes**
> The BLAST+ suite follows a conventional Unix exit-code scheme: 0 = success, 1 = usage
> error, 2 = NCBI database error, 3–6 = internal errors, 127 = command not found
> (shell convention), 255 = NCBI-specific remote error (rate limit, unknown). rc=-1 is
> a harness convention: the `TimeoutError` path sets `rc=-1` when the container's
> per-command timeout fires.
> Reference: https://www.ncbi.nlm.nih.gov/books/NBK279684/

### Updated `_summarize_blast_output` signature

The function now accepts `rc: int = 0`:

```python
def _summarize_blast_output(
    stdout: str,
    max_hits: int = 10,
    program: str = "blastn",
    version: str = "",
    rc: int = 0,
) -> str:
```

The dispatch logic follows a three-way branch:

```python
if not lines:
    if rc != 0:
        msg = _BLAST_RC_MESSAGES.get(
            rc, f"BLAST failed (rc={rc}) — see stderr. Do not interpret as 'no hits'."
        )
        return f"rc={rc}: {msg}"
    # rc=0, genuinely no hits
    installed_clause = ...
    return "No hits at default parameters. ..."
```

When `rc != 0` and stdout is non-empty (partial output before failure), the function
prepends a WARNING line to the hit table instead of replacing it:

```python
if rc != 0:
    msg = _BLAST_RC_MESSAGES.get(rc, ...)
    rows.insert(0, f"WARNING rc={rc}: {msg}")
    rows.insert(1, "Partial results:")
```

### Call-site update

In `AgentRun._loop()`, the call to `_summarize_blast_output` now passes `rc`:

```python
summary = _summarize_blast_output(
    stdout,
    max_hits,
    program=program,
    version=version,
    rc=rc,
)
```

The existing `if rc != 0:` stderr-prepend block at the call site is left intact — it
provides raw stderr context alongside the diagnostic from the summary. Together the
agent sees both the human-readable interpretation and the raw error output.

## 3. BP-2 — Species names via sscinames outfmt

### New constant: `_BLAST_OUTFMT`

BLAST tabular output format (`outfmt 6`) normally includes 12 standard fields. A custom
spec can append extra fields. This session adds `sscinames` (scientific species name) as
field 13:

```python
_BLAST_OUTFMT = (
    "6 qseqid sseqid pident length mismatch gapopen "
    "qstart qend sstart send evalue bitscore sscinames"
)
```

The command construction now uses this constant:

```python
command = (
    f"set -o pipefail; {program} -db {database} -query {query} "
    f'-outfmt "{_BLAST_OUTFMT}" '
    f"-max_target_seqs {max(max_hits * 2, 50)} "
    f"{remote} {extra} | tee {out_file}"
).strip()
```

> **📦 BLAST outfmt 6 custom fields**
> The standard `outfmt 6` spec produces 12 tab-separated columns in a fixed order.
> When you name fields explicitly (`outfmt "6 qseqid sseqid ..."`) you get exactly
> those fields in that order. `sscinames` returns the scientific name(s) of the
> subject sequence as a string (e.g. `"Homo sapiens"`, `"Bacillus licheniformis"`).
> For remote searches against nt/nr, NCBI returns this from its taxonomy database.
> Column indices are positional: `sscinames` lands at index 12 (0-based).

### Updated hit table

`_summarize_blast_output` now extracts sscinames and includes a Species column:

```python
sseqid    = parts[1]
pident    = parts[2]
evalue    = parts[10]
bitscore  = parts[11]
sscinames = parts[12].strip() if len(parts) > 12 else "N/A"

rows.append(
    f"{sseqid[:45]:<45} {sscinames[:32]:<32} {pident:>7}% {evalue:>12} {bitscore.strip():>9}"
)
```

The `len(parts) > 12` guard provides backward compatibility: if a cached
`blast_results.txt` from an older run has only 12 columns, the row still parses and
shows `"N/A"` for the species. The `len(parts) < 12` guard (malformed-row skip) is
unchanged.

## 4. BP-3 — Remote BLAST rate limiting

### State tracking

`AgentRun.__init__` gains one new float:

```python
self._last_blast_time: float = 0.0
```

### Enforcement

Immediately before each remote BLAST command, the dispatch checks the elapsed time since
the previous remote call:

```python
if remote:
    _min_interval = 1.0 / 3.0   # ≤3 calls/s per NCBI guidelines
    _elapsed = time.monotonic() - self._last_blast_time
    if _elapsed < _min_interval:
        time.sleep(_min_interval - _elapsed)
```

After the command completes (regardless of rc):

```python
if remote:
    self._last_blast_time = time.monotonic()
```

The `remote` variable is the `-remote` flag string — it is non-empty only when
`database` is `"nt"` or `"nr"`. Local BLAST databases never trigger the sleep or
update `_last_blast_time`.

> **📦 NCBI remote BLAST rate limits**
> NCBI permits up to 3 programmatic BLAST searches per second for anonymous access.
> Exceeding this triggers a `rc=255` response. The enforcement here adds at most
> 333 ms of wall-clock overhead per call, which is negligible compared to the
> multi-second latency of a remote BLAST search.
> Reference: https://www.ncbi.nlm.nih.gov/books/NBK153387/ (E-utilities guidelines)

## 5. BP-4 — blast-search SKILL.md rewrite

**File:** [`SKILLS/blast-search/SKILL.md`](../../SKILLS/blast-search/SKILL.md)

The SKILL file was rewritten with five structural changes:

1. **Topic index added** — eight numbered sections with their headings, making the
   document scannable.

2. **Query size guidance (§2)** — explicit 5000 bp limit for remote BLAST; instruction
   to extract a ≤1500 bp sub-region for longer sequences; explanation that oversized
   queries produce `rc=-1` (timeout), not "no hits".

3. **Exit code reference table (§5)** — mirrors `_BLAST_RC_MESSAGES` so the agent can
   cross-reference a numeric rc against the SKILL file; emphasises that `rc≠0` always
   means a tool or network failure, never "the organism isn't in the database."

4. **Recipe 1 replaced (§3)** — the original Recipe 1 was "Species identification from
   16S rRNA sequence", which is problem-specific (tied to bacterial identification
   problems like hb002). It was replaced with a generic "Nucleotide sequence search"
   recipe that applies to any nucleotide query without mentioning 16S, bacteria, or
   any specific organism group. See also BP-5.

5. **Rate limit note (§6)** — informs the agent that the tool enforces ≤3 calls/s
   automatically, so it should not attempt to loop BLAST calls faster than that.

The NCBI BLAST+ manual URL (`https://www.ncbi.nlm.nih.gov/books/NBK279684/`) is
referenced in the frontmatter and in the exit code section.

## 6. BP-5 — code-learnings L-28: no problem-specific SKILL content

**File:** [`.claude/skills/code-learnings/SKILL.md`](../../.claude/skills/code-learnings/SKILL.md)

The 16S recipe removal in BP-4 established a general principle. L-28 codifies it:

> **Rule:** New or updated SKILL files must not include problem-specific prompts.
> Prohibited: specific gene names, pathway names, organism names, or method guidance
> tied to a particular benchmark question. Such prompts artificially inflate
> performance on seen questions and do not generalise. Write SKILLs as methodology
> guides that apply to any question of that biological type.

The lesson distinguishes:
- **Prohibited:** "Use 16S rRNA BLAST to identify Bacillus species" (gene + organism)
- **Acceptable:** "Use `blastn` with `extra_args='-evalue 1'` to relax the threshold"
  (general parameter advice)

The five existing SKILL files were audited for violations. None required changes:
`deg-functional-enrichment.md` uses TP53/MYC as generic code examples (acceptable);
`chipseq-tf-identification.md` refers to hg38/mm10 as standard assemblies (standard
bioinformatics best practice, not problem-specific).

## 7. End-to-end data flow

A single `blast_search` tool call in `AgentRun._loop()`:

```
AgentRun._loop()
│
├── rate-limit check (if remote)
│   └── time.sleep(Δ) if too close to _last_blast_time
│
├── _get_blast_version(container, program)  [cached in _blast_versions]
│   └── container.exec_command("blastn -version", timeout=5)
│       → "blastn: 2.16.0\n" on success, "" on failure
│
├── if version == "": return early with "binary not found" error
│
├── command = f'set -o pipefail; blastn -db nt -query ... -outfmt "{_BLAST_OUTFMT}" ... | tee out_file'
│
├── container.exec_command(command, timeout=step_timeout_seconds)
│   → (stdout, stderr, rc)
│       stdout: TSV rows with 13 columns (qseqid…bitscore sscinames)
│       rc: 0 on success, -1 on timeout, 5 on network error, etc.
│
├── _last_blast_time = time.monotonic()  [if remote]
│
├── _summarize_blast_output(stdout, max_hits, program, version, rc)
│   ├── rc != 0, no lines → return rc-specific message from _BLAST_RC_MESSAGES
│   ├── rc != 0, has lines → prepend WARNING, then render hit table
│   └── rc == 0, no lines → "No hits at default parameters — consider …"
│       rc == 0, has lines → render hit table (Hit ID | Species | Identity | E-value | Bitscore)
│
└── tool_result content:
    "BLAST Summary (blastn vs nt):\n<summary>\n\nFull results saved to …"
    [prefixed with "BLAST error (rc=N):\n<stderr>" if rc != 0]
```
