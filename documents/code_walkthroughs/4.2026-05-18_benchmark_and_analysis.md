## 1. Why This Run Was Needed

The previous Cerebras/Qwen3 run (`results/cerebras-qwen3-clean/`, 2026-05-17) was
partially invalidated: hb022 and hb053 lost most attempts to Cerebras `queue_exceeded`
(429) errors that hit on the *first* API call, before the agent could do any work.
Exponential backoff (60 s → 120 s → 240 s, up to 4 retries) was subsequently added
to `OpenAIProvider.chat()` in `harness/llm.py`. This session re-ran the benchmark to
get a clean result set with the backoff in place.

The previous run's headline number was pass@5 = 20% (1/5 problems). The true number
with a working harness turned out to be 60% (3/5).

## 3. The Run Command and What Each Flag Does

```bash
echo "y" | python3 scripts/run_eval.py \
  --provider openai \
  --api-base-url https://api.cerebras.ai/v1 \
  --api-key $CEREBRAS_API_KEY \
  --model qwen-3-235b-a22b-instruct-2507 \
  --judge-model claude-haiku-4-5-20251001 \
  --results-dir results/cerebras-qwen3-clean-2 \
  --dataset preview \
  --n-attempts 5 \
  --no-build
```

| Flag | Value | Reason |
|------|-------|--------|
| `--provider openai` | `openai` | Cerebras uses an OpenAI-compatible API; this routes to `OpenAIProvider` |
| `--api-base-url` | `https://api.cerebras.ai/v1` | Overrides the default OpenAI base URL |
| `--api-key` | `$CEREBRAS_API_KEY` | Explicit key; avoids relying on env var parsing inside Click |
| `--model` | `qwen-3-235b-a22b-instruct-2507` | Current Cerebras Qwen3 model name (verified via preflight ping) |
| `--judge-model` | `claude-haiku-4-5-20251001` | Uses Haiku (Anthropic) to judge answers; without this flag the judge defaults to the agent model (Qwen3 self-judging) |
| `--results-dir` | `results/cerebras-qwen3-clean-2` | New directory — preserves the previous run |
| `--dataset preview` | `preview` | 5-problem HuggingFace split (full 99-problem requires HF approval) |
| `--n-attempts 5` | `5` | Standard pass@5 evaluation |
| `--no-build` | — | Docker image already present; skip the build step |
| `echo "y" \|` | — | Pipes "y" to the cost confirmation prompt (non-interactive) |

**Note on `--parallel`:** Defaults to 1. Sequential execution was intentional to avoid
compounding Cerebras 429 pressure.

**Note on critic:** `--critic-injection-points` was intentionally omitted to keep this
run comparable to the previous Cerebras benchmark. The comparative re-run with the

## 4. What --resume Actually Does (and Its Side-Effect)

The run was interrupted by a laptop shutdown mid-way through `recqgsfxqqodhjens`. After
Docker restarted, the benchmark was resumed with `--resume --no-build`.

**How `--resume` works:** Before each attempt, `is_attempt_complete()` in
`harness/logger.py` checks whether the trajectory file exists and contains a record
with a terminal status (`success`, `max_steps`, `timeout`, `token_limit`). If so, the
attempt is skipped.

**The side-effect (L-10):** `resource_abort` is *not* in that terminal status list.
This means any attempt that ended in `resource_abort` is re-run on resume. The new
attempt's result is appended to the `attempts` array in `scores.json`, but the
`total_attempts` counter and `pass_at_N` key are not recalculated. This leaves
`scores.json` in an inconsistent state for any problem that had aborted attempts.

```
# Example: hb020 in scores.json after resume
{
  "total_attempts": 4,     ← wrong; 6 attempts are in the attempts array
  "pass_at_4": true,       ← key reflects the pre-resume snapshot
  "attempts": [ ...6 entries... ]
}
```

**Rule:** When reading `scores.json` after a resumed run, verify
`len(attempts) == total_attempts`. If they disagree, use the `attempts` array
directly and ignore the pre-computed stats. Fix is tracked as pending slice (scoring
bug in `--resume` path).

## 6. Backoff Behaviour in Practice

The backoff in `OpenAIProvider.chat()` retries up to 4 times with delays 60 s, 120 s,
240 s before re-raising. It prints `[rate-limit] 429 on attempt N/4 — waiting Xs` to
stdout but does **not** log to the trajectory file (pending slice RL-1 to RL-5).

Observed backoff events across the run:

| Attempt | Backoffs fired | Total wait | Outcome |
|---------|---------------|-----------|---------|
| hb020 attempt 2 | 1 | 60 s | ✓ Completed (correct) |
| hb002 attempt 2 | 1 | 60 s | ✓ Completed (wrong) |
| hb002 attempt 4 | 1 | 60 s | ✓ Completed (wrong) |
| hb053 attempt 2 | 2 | 120 s | ✓ Completed (wrong) |
| hb053 attempt 3 | 3 | 180 s | ✓ Completed (wrong) |
| hb053 attempt 4 | 4 | 240 s | ✗ **Error** — retry budget exhausted |

5 of 6 attempts that hit a 429 recovered successfully. The one failure (hb053 attempt 4)
shows that sustained Cerebras congestion can exhaust all retries. Running during off-peak
hours reduces this risk.

**Key diagnostic fact (L-08):** These errors were infrastructure queue congestion, not
quota exhaustion. Actual usage was well under 10% of the account's RPM/TPM limits.

## 7. Trajectory Analysis: extract_final_answer Underscore Bug

**File:** `harness/scorer.py`, line 28

**Bug:** `_clean_answer()` applies:
```python
text = re.sub(r"\*{1,2}|_{1,2}", "", text)
```
This strips markdown bold/italic markers (`**text**`, `_text_`) but also destroys
bare underscores inside identifiers.

**Impact confirmed on hb022:**

The question instructs the model to format answers like `[Sample_01, Sample_02, ...]`.
The model's trajectory for attempt 2 ends with:
```
**FINAL ANSWER: [Sample_01, Sample_02, Sample_03, Sample_04, Sample_05, Sample_06, Sample_07, Sample_08]**
```
After `_clean_answer()` processes this:
```
[Sample01, Sample02, Sample03, Sample04, Sample05, Sample06, Sample07, Sample08]
```
The underscores are gone. The LLM judge then compares `Sample01` against the rubric's
`Sample_01` and marks it wrong.

Attempts 2 and 5 of hb022 were almost certainly correct answers that the scorer
failed. Fix is tracked as pending slice SC-1 to SC-4.

**How to spot this in future runs:** If `scores.json` shows a wrong answer but the
trajectory's FINAL ANSWER looks visually correct, run:
```python
from harness.scorer import extract_final_answer
print(repr(extract_final_answer("FINAL ANSWER: Sample_01")))
# Bug present:  'Sample01'
# Bug fixed:    'Sample_01'
```

## 8. Trajectory Analysis: Tool Availability Confusion

Trajectory analysis revealed three distinct tool-recognition failure modes:

### 8.1 blastn — rc=0 with empty stdout misread as "tool absent"

**Problem (hb002):** `blastn -db nt -remote` returned rc=0 with empty stdout (network
timeout or no hits). The agent concluded "blastn not available" and spent ~15 steps
per attempt attempting to reinstall it.

```
step 13 rc=0: blastn -query /workspace/data/anonymized_genome_1_.fasta -db nt -remote ...
  stdout: (empty)
  ← model interprets as: "blastn not installed"
  ← correct interpretation: "blastn ran, remote query returned no results"
```

rc=0 means the binary executed successfully. The model should have run
`blastn -version` to confirm availability, then retried the query or switched
approaches. Pending fix: SP-1/SP-2 (system prompt rule).

### 8.2 python3 and pip — installed but not on default $PATH

**Problem (recqgsfxqqodhjens, hb022):** `which python3` returns rc=1; `pip` returns
rc=127. Python and pip are installed inside the micromamba conda environment at
`/opt/conda/bin/` but this directory is not on `$PATH` in the default container shell.

```
step 22 rc=127: pip install bedtools
  stderr: bash: line 1: pip: command not found

step 25 rc=1:   which python3
  (no output)
```

The system prompt claims these tools are pre-installed, creating a false expectation.
Pending fix: ENV-1/ENV-2 (add `/opt/conda/bin` to `$PATH` in Dockerfile).

### 8.3 bedtools — absent from PATH (recqgsfxqqodhjens)

**Problem:** `bedtools getfasta` returns rc=127. micromamba install fails with a
backtrace error. This caused 4/7 attempts of recqgsfxqqodhjens to abort instead of
extracting peak sequences. The 2 correct attempts (CTCF) solved the problem through
reasoning from the BED file coordinates without needing bedtools.

Pending fix: ENV-4/ENV-5 (audit Dockerfile; add bedtools to image if missing).

## 9. scores.json Scoring Inconsistency

As described in §4, `--resume` re-runs `resource_abort` attempts and appends them
to `scores.json` without recalculating totals. After this session's run, three
problems have inconsistent entries:

| Problem | `total_attempts` | Actual entries in `attempts[]` | `pass_at_N` key |
|---------|-----------------|-------------------------------|-----------------|
| hb020 | 4 | 6 | `pass_at_4: true` |
| hb002 | 3 | 6 | `pass_at_3: false` ← hides the correct attempt 5 |
| recqgsfxqqodhjens | 5 | 7 | `pass_at_5: true` |

For hb002, the pre-computed `pass_at_3: false` is actively misleading — it hides
the fact that attempt 5 (the 5th original attempt, index 4 in the array) correctly
identified Bacillus licheniformis.

**Reading results correctly:** Always read `attempt_scores` and `attempts` arrays
directly; do not rely on `pass_at_N` keys after a resumed run with aborts.
