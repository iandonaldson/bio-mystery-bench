## 1. Background: Two Qwen3 Trajectory Failure Modes

The 2026-05-19 rerun (documented in
[`6.2026-05-19_rerun_postmortem.md`](6.2026-05-19_rerun_postmortem.md))
exposed four recurring failure modes in Qwen3-235B trajectories. Agent C
addressed two of them (single-round critic, missing `FINAL ANSWER` marker) in
[`7.Agent_C_walkthrough.md`](7.Agent_C_walkthrough.md). The remaining two are
the subject of this walkthrough.

**Failure mode 3 — Empty BLAST output mistaken for missing binary.**
On hb020 attempt 1, the agent ran `blast_search` against `nt`. The remote
NCBI BLAST query returned `rc=0` and an empty stdout — a perfectly valid
"no hits at default parameters" outcome. The harness summary at the time read
`"No BLAST hits found."`, which the model interpreted as evidence that the
binary itself was missing. It then spent ≈ 15 of its 30 step budget trying to
`pip install blast`, `apt-get install ncbi-blast+`, and re-run version checks
through python, exhausting the step budget before producing a final answer.
This is the canonical instance of the lesson recorded in
[`SKILLS/code-learnings/SKILL.md`](../../SKILLS/code-learnings/SKILL.md) §L-12 — *rc=0 with
empty stdout from a tool means no results, not tool absent.* L-12 added a
prompt-level rule; BE adds a harness-level fix so the agent does not have to
remember the rule.

**Failure mode 4 — Verbal critic with no actionable alternative.**
On hb002 attempt 4, the critic correctly identified a HIGH-risk assumption
("agent assumed *Bacillus licheniformis* ATCC 14580 and DSM 13 were the same
strain"). It ended with `"any HIGH-risk assumption would plausibly change the
final answer"`. The agent responded `"You raise a valid concern, however in the
literature these are generally treated as equivalent"` and re-stated its
original answer — no tool call, no verification, no alternative considered.
The critic prompt had no mechanism to force the critic to *list what the answer
might be instead*, and the injection wrapper had no mechanism to ask the agent
to *test* the alternative.

Both fixes are harness-level: the agent's behaviour is reasonable given the
prompts and outputs it sees; the harness has to give it better prompts and
outputs.

## 2. BE: Empty BLAST Disambiguation

### 2.1 Why `rc=0 + empty stdout` confused the agent

`blast_search` is a *summariser tool*: it runs the BLAST command inside the
container, tees the full tabular output (`outfmt 6`) to
`/workspace/scratch/blast_results.txt`, then returns a compact human-readable
table of the top hits to the model. The pre-BE summariser collapsed two very
different conditions into one identical message:

```
No BLAST hits found.
```

Condition A: BLAST ran successfully against an installed binary, but the
remote NCBI server returned no hits at the default parameters (high `evalue`
threshold, full-length query, etc.). Re-running with `-evalue 1` or
`-task blastn-short` would likely produce hits.

Condition B: BLAST is not installed. No amount of parameter tweaking will help;
the agent must install the binary first.

The same six-word message had to drive two opposite remediations. The agent
chose wrong (assumed B), and the step budget was burned.

BE replaces the summariser's empty-result branch with a message that
unambiguously confirms condition A — by quoting the version string of the
actual binary that just ran — and that lists four concrete things to try next.

### 2.2 `_get_blast_version` helper (BE-1)

**File:** [`harness/agent.py`](../../harness/agent.py)

`_get_blast_version` is a small module-level helper that runs `<program> -version`
inside the container and returns the first stdout line. It is called at most
once per program per run (the result is cached — see §2.3).

```python
def _get_blast_version(container: Container, program: str) -> str:
    """Run `<program> -version` in the container and return its first stdout line.

    Returns "" on non-zero exit, timeout, or any other failure. Used to disambiguate
    empty BLAST results from a missing binary (see L-12 in SKILLS/code-learnings/SKILL.md).
    """
    try:
        stdout, _stderr, rc = container.exec_command(f"{program} -version", timeout=5)
    except TimeoutError:
        return ""
    except Exception:
        return ""
    if rc != 0:
        return ""
    first_line = stdout.strip().splitlines()[0] if stdout.strip() else ""
    return first_line
```
[harness/agent.py:674–689](../../harness/agent.py)

**Design notes:**

- **5-second timeout.** Version checks should be fast (≪ 1 s on a healthy
  binary). 5 s is generous enough to absorb the docker-exec round-trip on a
  cold container but short enough that a hung binary does not stall a BLAST
  call.
- **Empty string on any failure.** The downstream summariser treats `""` as
  "version unknown" and omits the `installed (version …)` clause. There is no
  exception propagation — a missing binary is a possible condition, not a
  bug, so it should not crash the agent loop.
- **First line only.** BLAST `-version` outputs two or three lines (program
  name, package, build info). The first line is the canonical short form
  (`blastn: 2.13.0+`). Keeping it short keeps the embedded version readable in
  the agent's context window.

### 2.3 `_blast_versions` per-run cache (BE-2)

**File:** [`harness/agent.py`](../../harness/agent.py)

The cache lives on `AgentRun` so the version probe runs at most once per
program per attempt:

```python
self._critic_rounds: int = 0
self._blast_versions: dict[str, str] = {}
```
[harness/agent.py:220–221](../../harness/agent.py)

**Why per-run not per-process:**
- Each attempt gets a fresh container (see [`container.py`](../../harness/container.py)).
  A version probe against the previous attempt's container would be invalid
  the moment that container is torn down.
- The cache is read-once-write-once per program — the dictionary overhead is
  negligible compared to a single `docker exec` round-trip.

**Why this line broke during the post-mortem session:**
The original BE-2 commit was rebased onto Agent C's CR2-1, which had
simultaneously replaced `self._critic_injected = False` with
`self._critic_rounds: int = 0`. The rebase produced a one-line conflict
(both agents inserting a new attribute in the same place); the resolution was
to keep both. See [`SKILLS/code-learnings/SKILL.md`](../../SKILLS/code-learnings/SKILL.md)
§L-21 for the general lesson on parallel-agent `__init__` coordination.

### 2.4 `_summarize_blast_output` empty path (BE-3)

**File:** [`harness/agent.py`](../../harness/agent.py)

Pre-BE the signature was `_summarize_blast_output(stdout, max_hits=10)` and
the empty branch returned the six-word `"No BLAST hits found."` BE-3 extends
the signature with `program` and `version` and rewrites the empty branch:

```python
def _summarize_blast_output(
    stdout: str,
    max_hits: int = 10,
    program: str = "blastn",
    version: str = "",
) -> str:
    """Parse BLAST tabular output (outfmt 6) into a compact summary table.

    When there are no hits, the summary explicitly confirms the program is
    installed (citing `version` if provided) so the agent does not mistake an
    empty result for a missing binary (see L-12).
    """
    lines = [l for l in stdout.strip().splitlines() if l and not l.startswith("#")]
    if not lines:
        installed_clause = f" {program} installed (version {version})." if version else ""
        return (
            f"No hits at default parameters.{installed_clause} "
            "Anonymised sequences may not match nt/nr. "
            "Consider: (a) -evalue 1, (b) shorter query, "
            "(c) -task blastn-short for very short queries, "
            "(d) different program (blastn↔blastx)."
        )
    header = f"{'Hit ID':<45} {'Identity':>8} {'E-value':>12} {'Bitscore':>9}"
    ...
```
[harness/agent.py:692–712](../../harness/agent.py)

**Design notes:**

- **Backward compatibility.** Default values for `program` and `version` mean
  any pre-existing caller that does not pass them still works — the empty
  message just omits the `installed (version …)` clause. The three existing
  empty-path unit tests were updated to assert against `"No hits at default
  parameters."` and `"Consider:"` rather than the exact old string.
- **Non-empty path untouched.** The tabular summary (`Hit ID` header, separator,
  per-row formatting) is identical to the pre-BE version. The regression test
  `test_summarize_blast_non_empty_unchanged` pins this guarantee.
- **The four alternatives.** Each is a concrete, copy-pasteable BLAST flag or
  rewrite that the agent can try in its next call:
  - `(a) -evalue 1` — relax the default e-value of `1e-3` to accept weaker hits
  - `(b) shorter query` — long queries with no perfect match return zero hits;
    splitting into smaller fragments often yields partial matches
  - `(c) -task blastn-short` — BLAST has a dedicated mode for short (< 30 nt)
    queries; the default megablast mode skips them
  - `(d) different program` — translation-aware programs (`blastx`,
    `tblastn`) find homologues across the protein/nucleotide boundary that
    `blastn` misses
- **The "Anonymised sequences may not match nt/nr" hint.** Many problems in
  the benchmark use anonymised or synthetic sequences that have no nt/nr
  representation by construction. Steering the agent toward this possibility
  saves several wasted retries on the wrong premise.

### 2.5 BLAST dispatch in `_loop` (BE-4)

**File:** [`harness/agent.py`](../../harness/agent.py)

The `blast_search` branch of `_loop` now consults the cache and passes
both `program` and `version` into the summariser:

```python
if tool_call.name == "blast_search":
    query    = tool_call.input.get("query", "")
    database = tool_call.input.get("database", "nt")
    program  = tool_call.input.get("program", "blastn")
    max_hits = int(tool_call.input.get("max_hits", 10))
    extra    = tool_call.input.get("extra_args", "") or ""
    remote   = "-remote" if database in ("nt", "nr") else ""
    out_file = "/workspace/scratch/blast_results.txt"

    command = (
        f"{program} -db {database} -query {query} "
        f"-outfmt 6 -max_target_seqs {max(max_hits * 2, 50)} "
        f"{remote} {extra} | tee {out_file}"
    ).strip()

    self.logger.log("tool_call", {"blast_command": command})
    try:
        stdout, stderr, rc = self.container.exec_command(
            command,
            timeout=self.config.step_timeout_seconds,
        )
    except TimeoutError as e:
        stdout, stderr, rc = "", str(e), -1
    except Exception as e:
        stdout, stderr, rc = "", str(e), -1

    if program not in self._blast_versions:
        self._blast_versions[program] = _get_blast_version(
            self.container, program
        )
    summary = _summarize_blast_output(
        stdout,
        max_hits,
        program=program,
        version=self._blast_versions[program],
    )
```
[harness/agent.py:417–452](../../harness/agent.py)

**Critical sequencing detail:**
The version probe (`_get_blast_version`) is run *after* the BLAST command,
not before. Reasons:
1. The version is only consulted on the empty path. If BLAST returns hits, the
   tabular summary path is used and the version is never needed for *this*
   call (though it is still cached for any subsequent same-program call).
2. The version probe adds one extra `docker exec` round-trip (≈ 100 ms in
   typical Docker-on-Mac setups). Deferring it to the empty path keeps the
   non-empty path latency unchanged.
3. On a successful BLAST call, the binary self-evidently exists — proving it
   *also* exists via `-version` is redundant.

The cache miss test (`test_blast_search_caches_version_per_program`) drives
two consecutive `blast_search` calls of the same program and asserts that
`-version` was invoked exactly once.

> **📦 BLAST output format 6 (tabular)**
> The `-outfmt 6` flag tells BLAST to emit one tab-separated row per hit, with
> 12 standard columns: query id, subject id, percent identity, alignment length,
> mismatches, gap opens, q. start, q. end, s. start, s. end, e-value, bit score.
> The summariser parses these positionally (`parts[1]`, `parts[2]`, …) and
> formats columns 2, 3, 11, 12 (subject id, percent identity, e-value, bit
> score) into a fixed-width table. Rows with fewer than 12 fields are skipped
> rather than crashing the parser — gives robustness against truncated stdout
> from a timed-out remote call.

## 3. CP: Critic Prompt Requires Concrete Alternatives

### 3.1 Why "concerns remain" was not enough

The pre-CP `CRITIC_SYSTEM_PROMPT` asked the critic to:
1. State each unverified assumption
2. Explain how it would be verified
3. Rate the risk (HIGH / MEDIUM / LOW)
4. State whether any HIGH-risk assumption would change the answer

This produced reviews that read like: *"HIGH risk: agent assumed ATCC 14580
and DSM 13 are the same strain. Verification: query NCBI taxonomy or
literature. Yes, this could change the final answer."*

What the review did **not** include:
- **What the answer might be instead.** Without an alternative, the agent has
  nothing to test. It can verify the original assumption (which is what it
  always does), but it cannot consider a completely different strain identity.
- **Whether the original answer is *probably wrong* or *probably right but
  unverified*.** These two cases call for different agent responses — the
  first wants the agent to investigate alternatives, the second wants the
  agent to verify one specific assumption.

CP-1 forces alternatives + citations. CP-2 forces the binary distinction.
CP-3 closes the loop by telling the agent to test the alternative with the
strongest evidence support before re-stating its answer.

### 3.2 `CRITIC_SYSTEM_PROMPT` additions (CP-1, CP-2)

**File:** [`harness/agent.py`](../../harness/agent.py)

The full post-CP system prompt:

```python
CRITIC_SYSTEM_PROMPT = """\
You are a scientific reasoning auditor reviewing an AI agent's solution to a
computational biology problem. Your job is to identify assumptions the agent
made that were NOT empirically verified during the analysis.

For each unverified assumption:
1. State the assumption clearly
2. Explain what the agent would need to do to verify it
3. Rate the risk: HIGH (would likely change the conclusion if wrong),
   MEDIUM (might affect confidence but not conclusion), or LOW (minor)

Be concrete and specific — cite the actual reasoning steps where the assumption
was made. Do not flag assumptions that were explicitly tested.
Focus on the 2-3 most consequential unverified assumptions.

At the end, state whether any HIGH-risk assumption would plausibly change the
final answer if it turned out to be wrong.

For any HIGH-risk flag, list 1–2 alternative answers consistent with the
trajectory's evidence. Cite the specific trajectory step that supports each
alternative. Do not invent claims the agent did not make.

Distinguish two outcomes — (A) Agent answer appears wrong on the evidence
(list alternatives); (B) Agent answer may be correct but unverified (state
which assumption to verify).\
"""
```
[harness/agent.py:120–145](../../harness/agent.py)

**The two appended paragraphs (CP-1 and CP-2 respectively):**

- **CP-1 paragraph (alternatives + citations).** The phrase
  `"1–2 alternative answers"` caps the alternative count so the agent's
  context window does not balloon. The phrase `"Cite the specific trajectory
  step"` anchors each alternative in observable evidence; an alternative the
  critic invents from prior knowledge alone is rejected. The closing rule
  `"Do not invent claims the agent did not make"` is the single most
  important guardrail — without it, the critic can hallucinate evidence the
  agent never produced and then build alternatives on that hallucination.
- **CP-2 paragraph (outcome distinction).** The (A)/(B) binary feeds directly
  into the agent's response selection: outcome (A) triggers
  "test the strongest alternative" (CP-3 wrapper), outcome (B) triggers
  "verify the specific assumption" (existing wrapper bullet). The second
  critic round (CR2's `CRITIC_FOLLOWUP_PROMPT`) reuses this binary by mapping
  it to its three-way classification (`verified` / `verified-wrong` /
  `unverified-verbal-only`) — see
  [`7.Agent_C_walkthrough.md`](7.Agent_C_walkthrough.md) §2.3.

### 3.3 `_format_critic_injection` bullet (CP-3)

**File:** [`harness/agent.py`](../../harness/agent.py)

The injection wrapper is what the agent actually *sees* after the critic
fires — it wraps the critic's text in a `[CRITIC REVIEW]` envelope and adds
the agent's response checklist. CP-3 added one bullet:

```python
def _format_critic_injection(critique: str) -> str:
    return (
        "[CRITIC REVIEW]\n"
        "A scientific reasoning auditor has reviewed your analysis and identified "
        "the following concerns:\n\n"
        f"{critique}\n\n"
        "Please address any HIGH-risk concerns before finalising your answer:\n"
        "- If you agree with a concern, use bash to verify the assumption, then state "
        "your revised FINAL ANSWER.\n"
        "- If you disagree, briefly explain why and restate your original FINAL ANSWER.\n"
        "- If the critic listed alternatives, test the one with the strongest evidence "
        "support before restating your answer.\n"
        "You must end with: FINAL ANSWER: <answer>"
    )
```
[harness/agent.py:612–625](../../harness/agent.py)

**Position matters.** The new bullet sits between the original "agree /
disagree" bullets and the closing `"You must end with: FINAL ANSWER"` line.
This places the alternative-testing instruction *after* the agree/disagree
choice — so if the agent agrees with a concern, it can choose between
verifying its own assumption (existing bullet 1) or testing the critic's
alternative (new bullet 3). The wording `"strongest evidence support"` mirrors
the CP-1 requirement that each alternative cite a trajectory step; the agent
is being asked to pick the alternative with the strongest citation, not the
most plausible-sounding one.

### 3.4 Drive-by fix: missing `_final_answer_reprompted` initialiser

The CP-1 commit also added the one-line initialiser

had added a reference to this attribute inside `_loop` but never added the

This is documented in detail in
[`SKILLS/code-learnings/SKILL.md`](../../SKILLS/code-learnings/SKILL.md) §L-21. It is

shows changes to `__init__` that look unrelated to "critic prompt
alternatives" — they are unrelated, and the commit message is explicit about
the scope expansion.

## 4. End-to-end Flow: BLAST Returns No Hits

Scenario: agent issues a `blast_search` against `nt` with default params on an
anonymised query. NCBI returns rc=0 with empty stdout. (This is hb020 attempt
1 reproduced with the post-BE harness.)

```
┌─────────────────────────────────────────────────────────────┐
│ Agent (Qwen3): blast_search(query=...fasta, database=nt,    │
│                              program=blastn)                │
└─────────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────────┐
│ harness/agent.py _loop, blast_search branch                 │
│                                                             │
│ 1. container.exec_command("blastn -db nt -query ...         │
│                            -remote | tee ...")              │
│    → rc=0, stdout=""                                        │
│                                                             │
│ 2. cache miss: self._blast_versions["blastn"] not set       │
│    → _get_blast_version(container, "blastn")                │
│      → container.exec_command("blastn -version", timeout=5) │
│      → rc=0, stdout="blastn: 2.13.0+\nPackage: …"           │
│      → return "blastn: 2.13.0+"                             │
│    → cache["blastn"] = "blastn: 2.13.0+"                    │
│                                                             │
│ 3. _summarize_blast_output("", 10, program="blastn",        │
│                              version="blastn: 2.13.0+")    │
│    → lines=[] → empty branch                                │
│    → "No hits at default parameters. blastn installed       │
│       (version blastn: 2.13.0+). Anonymised sequences …     │
│       Consider: (a) -evalue 1, (b) shorter query, …"        │
│                                                             │
│ 4. result_text wrapped with "BLAST Summary (blastn vs nt):" │
│ 5. tool_result appended to messages                         │
└─────────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────────┐
│ Agent (Qwen3) reads tool_result                             │
│  - sees "blastn installed (version blastn: 2.13.0+)"        │
│    → does NOT attempt to reinstall                          │
│  - sees "Consider: (a) -evalue 1, …"                        │
│    → issues blast_search(..., extra_args="-evalue 1")       │
└─────────────────────────────────────────────────────────────┘
           │ (cache hit on second call: no second -version probe)
           ▼
       ... (gets hits this time, proceeds to FINAL ANSWER)
```

Compared to pre-BE: ≈ 15 steps saved per affected attempt (no install loop),
and the agent stays on the actual problem (parameter tuning) rather than a
nonexistent one (binary installation).

```
┌─────────────────────────────────────────────────────────────┐

│   → _run_critic(text, system_prompt=CRITIC_SYSTEM_PROMPT)  │
│     → critic API call                                       │

│       "HIGH risk: assumed ATCC 14580 = DSM 13 (step 12).   │
│        Alternative 1: DSM 13 — the agent's protein BLAST   │

│        reference set.                                       │
│        Outcome (A) Agent answer appears wrong on the       │

└─────────────────────────────────────────────────────────────┘
           │
           ▼
   (CR2 second critic round may follow if --critic-injection-points
    after_critic_response is set; see Agent C walkthrough §2.5)
```

The improvement vs pre-CP: the agent stops reasoning *about* the assumption
("treated as equivalent in the literature") and starts *testing* it (NCBI
query). The critic's job shifts from "warn" to "warn + give actionable
alternatives".

## 6. Testing

All new tests are in
[`tests/test_agent_helpers.py`](../../tests/test_agent_helpers.py).

### TestBlastVersionAndSummary (BE-1..4)

9 tests, one class. Split into three groups:

| Group | Test | What it verifies |
|------|------|-----------------|
| BE-1 helper | `test_get_blast_version_returns_first_line_on_success` | First stdout line returned on rc=0 |
| BE-1 helper | `test_get_blast_version_returns_empty_on_rc_nonzero` | rc=1 → `""` (no crash) |
| BE-1 helper | `test_get_blast_version_handles_timeout` | `TimeoutError` swallowed → `""` |
| BE-2 cache | `test_blast_versions_cache_initialised_empty` | `AgentRun._blast_versions == {}` after construction |
| BE-3 summary | `test_summarize_blast_empty_includes_version_when_provided` | `"blastn installed (version …)"` substring + `"Consider:"` substring |
| BE-3 summary | `test_summarize_blast_empty_omits_version_when_blank` | No `installed (version` when `version=""` |
| BE-3 summary | `test_summarize_blast_non_empty_unchanged` | Tabular path produces `Hit ID` header + per-row formatting; no `Consider:` / no `installed (version` |
| BE-4 dispatch | `test_blast_search_caches_version_per_program` | Two `blast_search` calls of same program → one `-version` call |
| BE-4 dispatch | `test_blast_search_empty_summary_includes_version_string` | End-to-end `run.run()` → tool_result message contains `blastn` and `blastn: 2.13.0+` |

The two BE-4 tests are *integration-style*: they construct a real `AgentRun`
with mocked `Provider` and mocked `Container` (each returning canned responses
matched by command-string substring), drive `run.run()` to completion, then
inspect the resulting `messages` list. They are the only tests in the suite
that exercise the `blast_search` dispatch end-to-end without Docker — and
also the tests that caught L-21's missing `_final_answer_reprompted`
initialiser when FA merged ahead of CP.

### TestCriticPromptAlternatives (CP-1..3)

3 tests, one class.

| Test | What it verifies |
|------|-----------------|
| `test_critic_system_prompt_requires_alternatives_with_evidence` | `CRITIC_SYSTEM_PROMPT` contains `"1–2 alternative answers"` and `"Cite the specific trajectory step"` |
| `test_critic_system_prompt_distinguishes_wrong_vs_unverified` | Contains `"Agent answer appears wrong on the evidence"`, `"may be correct but unverified"`, `"which assumption to verify"` |
| `test_critic_injection_wrapper_mentions_alternatives_testing` | `_format_critic_injection("dummy")` contains `"test the one with the strongest evidence support"` |

These are *substring tests*. They are deliberately permissive — they verify
the policy text is present without pinning the surrounding prose. This lets
future prompt-engineering passes refactor the wording without breaking CI, as
long as the load-bearing phrases survive.

### Updated existing tests

Three pre-existing tests in `TestSummarizeBlastOutput` (the BE-3 empty-path
tests written for the original `"No BLAST hits found."` message) were updated
to assert against the new substrings `"No hits at default parameters."` and
`"Consider:"`. The change is mechanical — they still test the same code path,
just with the new message.

## 8. Glossary

| Acronym | Spelled out | Notes |
|---------|------------|-------|
| **BE**  | BLAST Empty disambiguation | The four-sub-slice fix in PR #56 |
| **CP**  | Critic Prompt alternatives | The three-sub-slice fix in PR #59 |
| **CR2** | Critic Round 2 | Agent C's second-critic feature; see walkthrough #7 |
| **FA**  | Final Answer marker enforcement | Agent A's marker fix; see walkthrough #7 §3 |
| **rc**  | return code (Unix exit status) | `rc=0` = success in POSIX convention |
| **nt**  | NCBI nucleotide database | Default `blastn` database for unknown DNA sequences |
| **nr**  | NCBI non-redundant protein database | Default `blastp` database for unknown protein sequences |
| **outfmt 6** | BLAST tabular output format | 12 tab-separated columns; documented in BLAST+ manual |
| **e-value** | Expected number of chance hits | BLAST's default significance threshold is `1e-3` |
| **megablast** | BLAST's default DNA search algorithm | Optimised for highly similar sequences; skips short queries |
| **blastn-short** | BLAST mode for short queries | Use when query length < 30 nt |
