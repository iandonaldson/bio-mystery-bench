## 1. Background: Two Qwen3 Methodology Failures

The 2026-05-19 rerun (documented in
[`6.2026-05-19_rerun_postmortem.md`](6.2026-05-19_rerun_postmortem.md))
showed Qwen3-235B failing on two human-solvable problems for *methodological*
reasons rather than tooling reasons.

**Failure mode 5 — DEG list interpreted from sequence composition.**
On `hb053` (heat stress in *Brachypodium*), the question gave the agent a list
of ~50 differentially expressed genes (DEGs) and asked what biological
condition they reflected. Qwen3 ran the DEGs through a series of homemade
checks — GC content distribution, codon usage bias, a small k-mer scan — and
concluded "pathogen response" because some of the genes had higher AT content
than the genome mean. The actual condition (heat stress) is identifiable in
two seconds with an over-representation analysis (ORA) against MSigDB
hallmarks or GO biological process: the DEG list is enriched for `HSPA*`,
`DNAJ*`, and `HSF1` target genes, which collectively map to "Hallmark
response to heat shock" with an adjusted p-value well below 0.01.

The trajectory shows no attempt to query an annotation database. The model
treated the DEG list as a raw sequence set rather than as identifiers into
a curated functional knowledge graph. **This is not a tool problem** — the
model could trivially run `pip install gseapy` and 10 lines of Python — it is
a *methodology* problem: the model needed an authoritative pointer to *which*
method is the right one to reach for.

**Failure mode 6 — ChIP-seq TF identified by hand-picked k-mer counting.**
On `recqgsfxqqodhjens` (CTCF motif identification from ChIP-seq peaks), the
question provided ~5000 peak intervals and asked for the responsible
transcription factor. Qwen3 picked the first 10 peaks, extracted their
sequences with `bedtools getfasta`, counted the 6-mers by hand in a Python
loop, found a CG-rich repeat, and concluded "GC-binding TF" without ever
naming a specific factor or running a motif-database scan.

A standard JASPAR PWM scan over the full peak set returns `CTCF` (matrix
`MA0139.1`) with hits in 78% of peaks and a strong score margin over the
next candidate. Again the model has the tools (biopython is pre-installed;
`pyjaspar` is one `pip install` away) but lacks the methodological
direction.

**Common pattern.** Both failures share the same shape: the model substitutes
an ad-hoc sequence-level heuristic for an established database-lookup
methodology. The fix is therefore not new tooling but **better prompts** —
specifically, methodology guidance with concrete pointers to the right
recipes. GM operationalises this in two places:

1. Two new paragraphs in `prompts/system.txt` that name the right method
   (ORA/GSEA/GSVA; JASPAR/HOCOMOCO PWM scan) and forbid the wrong substitute
   (sequence composition; manual k-mer counting).
2. Two new versioned SKILL files (`deg-functional-enrichment`,
   `chipseq-tf-identification`) baked into `/workspace/skills/`, containing
   copy-pasteable Python recipes for each method. The agent can `cat` the
   file in-container without needing internet access.

The libraries themselves (`gseapy`, `pyjaspar`) are **not** baked into the
image — the brief deliberately chose install-on-demand so the image stays
under 4 GB and pinned-version drift is handled at problem-attempt time.

## 2. GM-1: DEG Functional-Interpretation Paragraph (§6)

**File:** [`prompts/system.txt`](../../prompts/system.txt) — appended to §6
(assumption checks), immediately before the final-answer-format paragraph.

The new paragraph adds three things in a single block: (a) the rule
("when interpreting DEGs, use enrichment against curated databases"),
(b) the three acceptable methods (ORA, GSEA, GSVA), and (c) the prohibition
on sequence-composition inference.

```text
   **Functional interpretation of gene lists.** When the question asks what
   condition, pathway, or perturbation a list of differentially expressed genes
   (DEGs) reflects, use a recognised enrichment method against curated annotation
   databases — do not infer the condition from sequence composition, GC content,
   codon usage, or any other property of the gene sequences themselves. Acceptable
   approaches:
   - Over-representation analysis (ORA) of the DEG list against Gene Ontology
     (biological process / molecular function / cellular component) or curated
     pathway collections (MSigDB hallmarks, KEGG, Reactome), applying
     Benjamini-Hochberg FDR correction to the hypergeometric p-values.
   - Gene Set Enrichment Analysis (GSEA) on the full ranked gene list (by log2
     fold change or signed test statistic) against the same collections.
   - Gene Set Variation Analysis (GSVA / ssGSEA) when per-sample pathway scores
     are needed rather than a single ranked list.
   Inferring "the genes look AT-rich, so this must be condition X" or
   "these genes share a k-mer motif, so the perturbation is Y" is not a valid
   substitute for an enrichment test against an annotated database. See
   `/workspace/skills/deg-functional-enrichment.md` for copy-pasteable recipes.
```

> **📦 ORA / GSEA / GSVA — three flavours of enrichment**
> *Over-representation analysis (ORA)* asks: of the genes in my list, how many
> belong to gene set X, and is that more than chance? Uses the hypergeometric
> distribution; needs only a list and a background. *Gene Set Enrichment
> Analysis (GSEA)* asks: when I rank all measured genes by effect size, does
> gene set X cluster toward the top or bottom? Uses a Kolmogorov-Smirnov-like
> running sum; needs the full ranked list. *Gene Set Variation Analysis (GSVA)*
> and its single-sample variant *ssGSEA* compute a pathway score *per sample*
> from the expression matrix, suitable for clustering or regression. All three
> use the same input gene sets (GO, MSigDB, KEGG, Reactome) but answer different
> questions.
> Further reading: [GSEA / MSigDB documentation](https://www.gsea-msigdb.org/gsea/index.jsp)

> **📦 Benjamini-Hochberg FDR**
> When a single enrichment run tests ~50 gene sets simultaneously, the raw
> p-values are not interpretable — even random gene lists hit
> `p < 0.05` in ~2-3 sets by chance. The Benjamini-Hochberg procedure controls
> the false-discovery rate (FDR) by ranking p-values and applying a stepwise
> threshold. Tools report it as `padj` or `q-value`; report only the adjusted
> value, never the raw one.

**Why the prohibition is explicit.** The trajectory analysis on `hb053`
showed Qwen3 picking the most plausible sequence-level feature it could
compute in-context (GC content, codon usage) and reasoning from there.
Without a written rule, the model has no reason to know that this approach
is methodologically rejected by the field. Forbidding it explicitly costs
five words of prompt and short-circuits an entire category of failure
trajectory.

**Anchor for GM-3.** The final line points at
`/workspace/skills/deg-functional-enrichment.md`, the in-container file
created by GM-3 (§4 below). The agent does not need to remember the recipes
— it only needs to remember to `cat` the file.

## 3. GM-2: ChIP-seq TF Motif Lookup Paragraph (§3c)

**File:** [`prompts/system.txt`](../../prompts/system.txt) — appended as
step 3c in the "General approach" numbered list, immediately after the
BLAST-tool guidance from 3b.

```text
3c. **TF identification from ChIP-seq peaks.** To identify the transcription
    factor (or candidate TFs) responsible for a set of ChIP-seq peaks, extract
    the peak-flanking sequences with `bedtools getfasta` (typically ±100 bp
    around the peak summit) and scan them against a curated motif database
    such as JASPAR or HOCOMOCO, using `pyjaspar` together with `Bio.motifs`
    PWM scoring or the JASPAR REST API. Manually counting k-mers in a hand-
    picked subset of peaks is not a substitute for a motif database scan and
    will not identify the responsible TF reliably. See
    `/workspace/skills/chipseq-tf-identification.md` for copy-pasteable recipes.
```

> **📦 JASPAR**
> An open-access database of curated transcription factor binding profiles
> (PWMs / PFMs). Each profile has a stable matrix ID (`MA0139.1` = CTCF v1)
> and is grouped into collections (CORE = experimentally validated;
> PBM/HOCOMOCO/UniPROBE = other sources). The Python wrapper `pyjaspar`
> exposes the catalogue locally; the REST API at
> `https://jaspar.genereg.net/api/v1/` serves the same data. Releases follow
> a year-based schema (`JASPAR2024`).
> Further reading: [JASPAR documentation](https://jaspar.genereg.net/docs/)

> **📦 PWM scoring**
> A *position-weight matrix (PWM)* is a 4×L matrix of log-odds scores —
> one row per nucleotide (A/C/G/T), one column per position in the motif.
> Scoring a sequence means sliding the matrix along it, summing the
> log-odds at each position, and recording the best hit. A score above a
> distribution-derived threshold (e.g. the 99.9th percentile of random
> background scores) counts as a binding-site hit. `Bio.motifs.pssm`
> implements this; `pyjaspar` provides the motifs.

**Anchor location.** Step 3 in the General approach is "Choose appropriate
tools given available resources". 3a and 3b already cover tool-availability
patterns (rc=0+empty stdout) and the `blast_search` tool. 3c slots naturally
into the same pattern: a domain-specific methodology rule with a pointer to
the in-container recipe.

## 4. GM-3: `deg-functional-enrichment` SKILL

**File:** [`SKILLS/deg-functional-enrichment/SKILL.md`](../../SKILLS/deg-functional-enrichment/SKILL.md)
(new directory + new file).

The SKILL follows the project convention (YAML frontmatter, then markdown
body) established by [`SKILLS/analyze-trajectories/SKILL.md`](../../SKILLS/analyze-trajectories/SKILL.md).
Frontmatter:

```yaml
---
name: deg-functional-enrichment
description: >
  Functional enrichment recipes for a list of differentially expressed genes
  (DEGs). Three copy-pasteable approaches: over-representation analysis (ORA)
  against Enrichr libraries, Gene Set Enrichment Analysis (GSEA) on a ranked
  gene list against an MSigDB GMT file, and single-sample GSEA (ssGSEA, the
  GSVA-equivalent in gseapy) for per-sample pathway scores. Use this skill
  whenever a problem asks what condition, pathway, or perturbation a DEG list
  reflects — do not infer the answer from sequence properties.
---
```

The body opens with the install-on-demand note (`pip install gseapy`), then
an organism-to-collection guide (Hallmark for human/mouse, KEGG/Reactome for
broader pathway coverage, GO for organisms outside human/mouse), then three
recipes — one per method.

> **📦 gseapy**
> A pure-Python implementation of the GSEA family of methods. Wraps three
> things in one library: (a) the Enrichr REST API (`gp.enrichr`) for ORA,
> (b) a port of the Broad Institute's prerank GSEA (`gp.prerank`),
> (c) a port of ssGSEA / single-sample GSEA (`gp.ssgsea`). Same gene-set
> input format (`.gmt` files or Python dicts) across all three. Not in the
> Docker image — install with `pip install gseapy` when the agent first
> encounters a DEG-interpretation problem.
> Further reading: [gseapy documentation](https://gseapy.readthedocs.io/)

> **📦 MSigDB / Enrichr**
> *MSigDB (Molecular Signatures Database)* is the Broad Institute's
> curated collection of gene sets — Hallmark (50 phenotype sets, the
> default starting point for human/mouse), C2 (curated pathways including
> KEGG/Reactome), C5 (Gene Ontology), etc. Distributed as `.gmt` files.
> *Enrichr* is the Ma'ayan Lab's hosted enrichment service — it ships its
> own continuously-updated mirror of MSigDB plus many other libraries
> (GO_Biological_Process_2023, Reactome_2022, etc.) and exposes them via
> a REST API. `gp.enrichr` calls Enrichr; `gp.prerank` reads MSigDB
> `.gmt` files locally or from a library name.
> Further reading: [MSigDB](https://www.gsea-msigdb.org/gsea/msigdb/), [Enrichr](https://maayanlab.cloud/Enrichr/)

### Recipe 1 — ORA via `gp.enrichr`

For a single up- or down-regulated gene list with no per-gene ranking.
Calls the Enrichr REST API; no local database files required.

```python
import gseapy as gp

deg_list = ["TP53", "CDKN1A", "BAX", "MDM2", "PUMA", "NOXA"]

enr = gp.enrichr(
    gene_list=deg_list,
    gene_sets=[
        "MSigDB_Hallmark_2020",
        "KEGG_2021_Human",
        "Reactome_2022",
        "GO_Biological_Process_2023",
    ],
    organism="Human",
    outdir=None,
    cutoff=0.05,
)

top = enr.results.sort_values("Adjusted P-value").head(20)
```

### Recipe 2 — GSEA via `gp.prerank`

For a full ranked gene list (e.g. all measured genes sorted by signed
log2 fold change). Tests whether members of each set cluster toward
the top or bottom.

```python
import gseapy as gp
import pandas as pd

rnk = pd.DataFrame({
    "gene": [...],
    "rank": [...],     # signed log2FC or t-stat
}).sort_values("rank", ascending=False)

res = gp.prerank(
    rnk=rnk,
    gene_sets="MSigDB_Hallmark_2020",
    threads=4,
    permutation_num=1000,
    outdir=None,
    seed=42,
    min_size=15,
    max_size=500,
)
top = res.res2d.sort_values("FDR q-val").head(20)
```

### Recipe 3 — ssGSEA via `gp.ssgsea`

For a full expression matrix when per-sample pathway scores are needed.
Output is a `samples × pathways` matrix of normalised enrichment scores
suitable for clustering or regression.

```python
import gseapy as gp
import pandas as pd

expr = pd.read_csv("expression_matrix.tsv", sep="\t", index_col=0)

ss = gp.ssgsea(
    data=expr,
    gene_sets="MSigDB_Hallmark_2020",
    outdir=None,
    sample_norm_method="rank",
    no_plot=True,
    threads=4,
)

scores = ss.res2d.pivot(index="Name", columns="Term", values="NES")
```

The body closes with a decision table — "which recipe for which input
shape" — so the agent can pick without re-reading the recipes.

## 5. GM-4: `chipseq-tf-identification` SKILL

**File:** [`SKILLS/chipseq-tf-identification/SKILL.md`](../../SKILLS/chipseq-tf-identification/SKILL.md)
(new directory + new file).

Same structure as GM-3 (frontmatter + body + decision table) but two recipes
instead of three: a local PWM scan and a JASPAR REST API query.

> **📦 pyjaspar + Bio.motifs**
> *`pyjaspar`* downloads and caches a release of JASPAR's full motif
> catalogue (`JASPAR2024` has ~700 vertebrate motifs in the CORE collection
> alone) and returns each as a `Bio.motifs.Motif` object. *`Bio.motifs`*
> (part of `biopython`, already pre-installed in the Docker image) provides
> the PWM-scoring machinery — `motif.counts.normalize(pseudocounts=0.5)`
> builds a PWM, `.log_odds()` converts to a PSSM, `pssm.calculate(seq)`
> scores a sequence, and `pssm.distribution().threshold_fpr(0.001)` derives
> a score threshold at a false-positive rate of 0.1%. Together they let
> an agent score 5000 peaks against 700 motifs in under a minute on the
> default container.

### Recipe 1 — Local PWM scan

Three-stage pipeline: extract peak summits (or centres if no summit) →
slop ±100 bp → `bedtools getfasta` → score each FASTA record against every
JASPAR CORE motif. Returns a ranked count of "peaks with ≥ 1 hit per motif".

```bash
# Step 1: extract ±100 bp around each peak summit.
awk 'BEGIN{OFS="\t"} {summit=$2+$10; print $1, summit-100, summit+100}' \
    peaks.narrowPeak > peaks.flanks.bed

bedtools getfasta -fi /path/to/genome.fa -bed peaks.flanks.bed -fo peaks.flanks.fa
```

```python
from pyjaspar import jaspardb
from Bio import motifs, SeqIO
from Bio.Seq import Seq
import collections

jdb = jaspardb(release="JASPAR2024")
core_motifs = jdb.fetch_motifs(collection="CORE", tax_group=["vertebrates"])

pssms = []
for m in core_motifs:
    pwm = m.counts.normalize(pseudocounts=0.5)
    pssms.append((m.matrix_id, m.name, pwm.log_odds()))

hits = collections.Counter()
for rec in SeqIO.parse("peaks.flanks.fa", "fasta"):
    seq = Seq(str(rec.seq).upper().replace("N", "A"))
    for matrix_id, name, pssm in pssms:
        threshold = pssm.distribution(precision=10**3).threshold_fpr(0.001)
        best = max(pssm.calculate(seq).max(),
                   pssm.reverse_complement().calculate(seq).max())
        if best >= threshold:
            hits[(matrix_id, name)] += 1

for (mid, name), n in hits.most_common(20):
    print(f"{mid:12s} {name:20s} {n}/{total_peaks} ({100*n/total_peaks:.1f}%)")
```

### Recipe 2 — JASPAR REST API

For metadata lookup or small-scale scanning without downloading the local
catalogue:

```python
import requests

JASPAR_API = "https://jaspar.genereg.net/api/v1"

r = requests.get(
    f"{JASPAR_API}/matrix/",
    params={"tax_group": "vertebrates", "collection": "CORE", "page_size": 500},
    timeout=30,
)
matrices = r.json()["results"]
```

The body also includes guidance on choosing the genome assembly
(hg38 / mm10 must match the assembly the peaks were called against) and
flank width (±100 bp default; ±50 bp for very sharp peaks; ±250 bp for
broad-peak data).

## 6. GM-5: Baking SKILLs into the Docker Image

**File:** [`docker/Dockerfile`](../../docker/Dockerfile).

Three changes to the Dockerfile:

1. The `mkdir -p` line gains `/workspace/skills` so the COPY targets exist.
2. Two `COPY SKILLS/.../SKILL.md /workspace/skills/<name>.md` directives.
3. The existing `COPY entrypoint.sh /entrypoint.sh` becomes
   `COPY docker/entrypoint.sh /entrypoint.sh` to remain valid under the
   new build context (see §12 below).

```dockerfile
RUN mkdir -p /workspace/data /workspace/scratch /workspace/output /workspace/skills
WORKDIR /workspace

# Bio method reference recipes. Source of truth lives at SKILLS/<name>/SKILL.md
# in the repo root — these copies are baked into /workspace/skills/ so the agent
# can `cat` them in-container without needing internet access.
# NOTE: requires `docker build -f docker/Dockerfile .` from the repo root (not
# `docker build docker/`); see scripts/smoke_test_container.py for the canonical
# rebuild command.
COPY SKILLS/deg-functional-enrichment/SKILL.md /workspace/skills/deg-functional-enrichment.md
COPY SKILLS/chipseq-tf-identification/SKILL.md /workspace/skills/chipseq-tf-identification.md

COPY docker/entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
```

**No `pip install gseapy pyjaspar`.** The brief explicitly directed
install-on-demand: the library footprint would add ~120 MB to a 4 GB image
without commensurate benefit, and library versions drift faster than the
image is rebuilt. The agent installs at problem-attempt time.

gets two new entries in its `CHECKS` list:

```
                       │
```

```
6. Agent writes the Python scoring loop (recipe verbatim — score each
   peak FASTA against JASPAR2024 CORE vertebrates, count peaks per
   motif above the FPR=0.001 threshold).
                       │
                       ▼
7. Top hit: MA0139.1 (CTCF) — 3,892/5,000 peaks (77.8%).
                       │
                       ▼
8. Agent reaches §6's final-answer assumption check, verifies the
   score margin over the next candidate is large, states the answer.
                       │
                       ▼
9. FINAL ANSWER: CTCF
```

The flow is structurally identical to the DEG case — the difference is
that the ChIP-seq recipe has a `bedtools getfasta` preprocessing step
that the DEG recipe doesn't need.

## 12. Build-Context Tension: Why the COPY Paths Required a Workaround

The most subtle thing in PR #60 is **not** in the diff — it is the latent
incompatibility between the new `COPY SKILLS/...` paths and
`scripts/run_eval.py:ensure_docker_image()`, which the brief explicitly
forbade Agent A from touching.

The Dockerfile's `COPY SKILLS/...` requires the build context to include
the `SKILLS/` directory — i.e. the build must be invoked with the repo
root as the context, not the `docker/` subdirectory:

```bash
# Correct (PR #60 onward):
docker build -t bio-mystery-bench:latest -f docker/Dockerfile .

# Incorrect (the historical invocation in ensure_docker_image and README):
docker build -t bio-mystery-bench:latest docker/
```

`scripts/run_eval.py:ensure_docker_image()` still passes the `docker/`
directory as the build context — and `README.md` quick-start documents
the same invocation. Both will fail the next time the image cache is
cleared and `docker image inspect` returns non-zero, triggering an
auto-rebuild.

This is a **latent bug**, not a regression: the currently cached
`bio-mystery-bench:latest` image satisfies `docker image inspect`, so
`ensure_docker_image()` short-circuits to "image found" and never invokes
`docker build` at all. Live runs keep working. The failure mode appears
only on a fresh machine, a CI environment without the cached image, or
after a manual `docker rmi`.

The reasoning behind shipping the latent bug (recorded in
[`SKILLS/code-learnings/SKILL.md`](../../SKILLS/code-learnings/SKILL.md) §L-22):

1. The brief was explicit about file-list scope. Touching `run_eval.py`
   would have violated the orchestration constraint and could have
   conflicted with Agent B/C's PRs.
2. The fix is one-line and trivially independent — adding
   `"-f", str(dockerfile_dir / "Dockerfile"), str(dockerfile_dir.parent)`
   to the subprocess call.
3. Flagging the gap loudly (PR body, `claude-progress.txt` → Next steps
   #1, this walkthrough §12, learning L-22) is preferable to silent
   compliance with hidden breakage.

The fix is the first item in `claude-progress.txt` → Next steps and is
expected to land in a small follow-up PR before the next image rebuild
is needed.

## 13. Glossary

| Acronym | Spelled out | Notes |
|---------|------------|-------|
| **GM**  | General Method advice + reference SKILLs | The six-sub-slice fix in PR #60 |
| **DEG** | Differentially Expressed Gene | A gene with a statistically significant change in expression between two conditions |
| **TF**  | Transcription Factor | A protein that binds DNA in a sequence-specific manner to regulate gene expression |
| **ORA** | Over-Representation Analysis | Hypergeometric test of whether a gene list is enriched for a curated set |
| **GSEA** | Gene Set Enrichment Analysis | Kolmogorov-Smirnov-style enrichment test on a fully ranked gene list |
| **GSVA** | Gene Set Variation Analysis | Per-sample pathway-score variant of GSEA |
| **ssGSEA** | single-sample GSEA | gseapy's name for GSVA's default method |
| **FDR** | False Discovery Rate | Multiple-testing correction; report `padj` or `q-value`, never raw `p` |
| **BH**  | Benjamini-Hochberg | The standard procedure for controlling FDR |
| **GO**  | Gene Ontology | Three-axis controlled vocabulary: biological process, molecular function, cellular component |
| **MSigDB** | Molecular Signatures Database | Broad Institute curated gene-set collection (Hallmark, C2, C5, etc.) |
| **KEGG** | Kyoto Encyclopedia of Genes and Genomes | Curated pathway database |
| **PWM** | Position-Weight Matrix | 4×L matrix of log-odds scores; the standard motif representation |
| **PFM** | Position-Frequency Matrix | 4×L matrix of raw counts; converts to PWM via normalisation |
| **PSSM** | Position-Specific Scoring Matrix | PWM after log-odds conversion; used for sequence scoring |
| **FPR** | False-Positive Rate | Threshold parameter for PWM-score significance |
| **JASPAR** | (project name) | Open-access curated transcription factor binding profile database |
| **HOCOMOCO** | HOmo sapiens COmprehensive MOdel COllection | Alternative motif database; complementary to JASPAR for human/mouse TFs |
| **hg38** | Human Genome 38 (GRCh38) | Current standard human reference assembly |
| **mm10** | Mouse Genome 10 (GRCm38) | Current standard mouse reference assembly |
| **GMT** | Gene Matrix Transposed | File format for gene-set collections (`<name>\t<description>\t<gene>\t<gene>...`) |
