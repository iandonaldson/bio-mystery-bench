## 1. Background: The Qwen3 Post-Mortem Problem

The 2026-05-19 benchmark rerun (documented in
[`6.2026-05-19_rerun_postmortem.md`](6.2026-05-19_rerun_postmortem.md)) revealed
two recurring failure modes in Qwen3-235B trajectories that also appeared — less
frequently — in Claude Sonnet trajectories:

**Failure mode 1 — Verbal-only critic responses.** The critic (round 1) correctly
identified a HIGH-risk assumption: for example, in hb002 attempt 4, the critic
flagged that the agent assumed Bacillus licheniformis ATCC 14580 and DSM 13 were
the same strain. The agent's follow-up response was: "You raise a valid concern —
however, in the literature these are generally treated as equivalent." No tool call
was made. The assumption was never verified. The harness accepted the response as
complete. With a single critic round, there was no mechanism to detect that the
remediation was verbal-only rather than empirical.

**Failure mode 2 — Missing FINAL ANSWER marker.** Some Qwen3 attempts terminated
without the `FINAL ANSWER: <text>` line required by the system prompt.
`extract_final_answer` fell back to the last non-empty line of the response, which
was often a reasoning sentence rather than the answer. The extractor silently
returned the wrong value, and the attempt scored wrong.

Both problems are harness-level: the agent's behaviour is not wrong given the system
prompt, but the harness has no feedback loop to correct it. CR2 and FA add those
feedback loops.

## 2. CR2: Second Critic Exchange

### 2.1 Why one critic round is not enough

The original single-critic design (PR #26, documented in
[`3.Accommodating_OpenAI_models.md`](3.Accommodating_OpenAI_models.md) §5) worked
as follows:

```
agent end_turn → critic fires once → agent responds → success
```

The critic's role was to identify unverified HIGH-risk assumptions. But it had no
way to verify that the agent actually tested those assumptions in its follow-up
response. A verbal acknowledgement looks identical to a genuine tool-call
verification in the message history, because both produce an `end_turn` response.

The second critic exchange (CR2) adds:

```
agent end_turn → critic round 1 → agent responds → critic round 2 (followup audit) → agent responds → success
```

Round 2 asks the critic to classify each prior HIGH-risk concern as:
- `verified` — agent ran a tool call that confirmed the assumption
- `verified-wrong` — agent ran a tool call that contradicted the assumption
- `unverified-verbal-only` — agent only argued, without testing

If any concern is `unverified-verbal-only`, the critic lists 1–2 alternative answers
consistent with the collected evidence.

### 2.2 `_critic_rounds` replaces `_critic_injected`

**File:** [`harness/agent.py`](../../harness/agent.py)

The original single-round design used a boolean flag:

```python
# Before CR2-1 (PR #26)
self._critic_injected = False

# In _loop end_turn branch:
if "after_final_answer" in cp and not self._critic_injected:
    self._critic_injected = True
    ...
```

A boolean cannot express how many rounds have fired. CR2-1 replaced it with an
integer counter:

```python
# After CR2-1 (PR #57)
self._critic_rounds: int = 0

# In _loop end_turn branch:
if "after_final_answer" in cp and self._critic_rounds == 0:
    self._critic_rounds += 1
    ...
```

This is a pure refactor — behaviour is identical when only `after_final_answer` is
configured, because `self._critic_rounds == 0` is equivalent to
`not self._critic_injected` on the first end_turn.

> **📦 Why start from zero?**
> `_critic_rounds` counts completed rounds, not pending ones. Before any critic
> fires, it is 0. After round 1 fires, it is 1. This lets `>= 1` unambiguously
> mean "a first-round critique has been delivered" — the precondition for the
> followup prompt.

### 2.3 `CRITIC_FOLLOWUP_PROMPT` — the round-2 audit

**File:** [`harness/agent.py`](../../harness/agent.py)

A new module-level constant provides the round-2 system prompt:

```python
CRITIC_FOLLOWUP_PROMPT = """\
You previously audited this agent's reasoning. The agent has now responded.
Review the new tool calls and reasoning since your last critique.

For each HIGH-risk assumption you flagged: (a) did the agent empirically test
it via a tool call? Mark each as one of:
- verified           — the agent ran a tool call that confirmed the assumption
- verified-wrong     — the agent ran a tool call that contradicted the assumption
- unverified-verbal-only — the agent only re-stated or argued, without testing

If any HIGH-risk assumption remains unverified-verbal-only, list 1-2 alternative
answers that would also be consistent with the evidence collected so far.

Conclude with a one-line verdict: 'concerns resolved' or 'concerns remain'.\
"""
```

Key design decisions:
- **Three classification labels** give the critic a precise vocabulary. `verified`
  and `verified-wrong` both require a tool call; only `unverified-verbal-only` flags
  evasion.
- **Listing alternatives** gives the agent something concrete to test, rather than
  re-stating the same abstract concern.
- **One-line verdict** produces a machine-readable (or easily human-readable)
  summary at the end of every round-2 critique.

Compare to `CRITIC_SYSTEM_PROMPT` (round 1):

```python
CRITIC_SYSTEM_PROMPT = """\
You are a scientific reasoning auditor reviewing an AI agent's solution to a
computational biology problem. Your job is to identify assumptions the agent
made that were NOT empirically verified during the analysis.
...
"""
```

Round 1 asks *what* the agent has not tested. Round 2 asks *whether* the agent
tested it after being told to.

### 2.4 Config changes — `harness/config.py`

**File:** [`harness/config.py`](../../harness/config.py)

Two additions:

```python
# Before CR2-2
CRITIC_INJECTION_POINTS = ("after_final_answer",)

# After CR2-2
CRITIC_INJECTION_POINTS = ("after_final_answer", "after_critic_response")
```

`"after_critic_response"` is the identifier for the second injection point — it
fires after the agent has responded to the round-1 critique.

```python
@dataclass
class RunConfig:
    ...
    critic_injection_points: list = field(default_factory=list)
    critic_model: str = ""
    max_critic_rounds: int = 2          # ← new in CR2-2
```

`max_critic_rounds` caps the number of critic exchanges per run. Default is 2
(one round-1 audit, one round-2 followup). Setting it to 1 restores the old
single-round behaviour even if `after_critic_response` is in the injection points.

> **Why a cap?** Without one, if the critic always returns a non-empty response
> (even "concerns resolved"), and `after_critic_response` is enabled, `_loop`
> would call the critic indefinitely. `max_critic_rounds` is a hard ceiling so
> the harness cannot loop forever regardless of what the critic returns.

### 2.5 `_loop`: multi-round injection logic

**File:** [`harness/agent.py`](../../harness/agent.py), `_loop()` method

The original single-round condition:

```python
# Before CR2-4
if "after_final_answer" in cp and self._critic_rounds == 0:
    self._critic_rounds += 1
    critique = self._run_critic(response.text)
```

The new multi-round condition:

```python
# After CR2-4
cp = self.config.critic_injection_points
fire_critic = (
    self._critic_rounds < self.config.max_critic_rounds
    and (
        ("after_final_answer" in cp and self._critic_rounds == 0)
        or ("after_critic_response" in cp and self._critic_rounds >= 1)
    )
)
if fire_critic:
    system_prompt = (
        CRITIC_FOLLOWUP_PROMPT
        if self._critic_rounds >= 1
        else CRITIC_SYSTEM_PROMPT
    )
    self._critic_rounds += 1
    critique = self._run_critic(response.text, system_prompt=system_prompt)
```

Walking through the logic:

| `_critic_rounds` before this end_turn | `after_final_answer` in cp | `after_critic_response` in cp | `fire_critic` | System prompt used |
|---:|:---:|:---:|:---:|:---|
| 0 | ✓ | ✓ | True | `CRITIC_SYSTEM_PROMPT` |
| 1 | ✓ | ✓ | True | `CRITIC_FOLLOWUP_PROMPT` |
| 2 | ✓ | ✓ | False (cap reached) | — |
| 0 | ✓ | ✗ | True | `CRITIC_SYSTEM_PROMPT` |
| 1 | ✓ | ✗ | False (not in cp) | — |

The counter increments **before** `_run_critic` is called (line 3 of the `if
fire_critic` block), so if `_run_critic` raises an exception, the round is still
counted. This prevents infinite retries: a failing critic still advances the counter
and the harness eventually exits the critic loop.

### 2.6 `_run_critic`: new `system_prompt` parameter

**File:** [`harness/agent.py`](../../harness/agent.py)

```python
# Before CR2-4
def _run_critic(self, final_answer: str) -> str:
    ...
    response = self.critic_client.chat(
        model=critic_model,
        system=CRITIC_SYSTEM_PROMPT,
        ...
    )

# After CR2-4
def _run_critic(self, final_answer: str, system_prompt: str = CRITIC_SYSTEM_PROMPT) -> str:
    ...
    response = self.critic_client.chat(
        model=critic_model,
        system=system_prompt,
        ...
    )
```

The default value `CRITIC_SYSTEM_PROMPT` preserves backwards compatibility: any
call site that does not pass `system_prompt` gets the original round-1 behaviour.
The caller (`_loop`) passes `CRITIC_FOLLOWUP_PROMPT` explicitly for rounds ≥ 1.

### 2.7 Trajectory logging: round number

Each `critic` log event now includes a `round` field:

```python
self.logger.log("critic", {
    "model": self.config.critic_model or self.config.model,
    "critique": critique,
    "round": self._critic_rounds,   # ← new in CR2-4
})
```

`_critic_rounds` has already been incremented at this point, so `round=1` means
"this is the first critic response" and `round=2` means "this is the second".
This makes it easy to distinguish first-pass and follow-up critiques when reading
a trajectory file.

### 2.8 CLI additions — `scripts/run_eval.py`

**File:** [`scripts/run_eval.py`](../../scripts/run_eval.py)

Two changes to the Click command:

```python
# Before CR2-5
@click.option("--critic-injection-points", multiple=True,
              type=click.Choice(["after_final_answer"]),
              ...)

# After CR2-5
@click.option("--critic-injection-points", multiple=True,
              type=click.Choice(["after_final_answer", "after_critic_response"]),
              ...)
@click.option("--max-critic-rounds", default=2, show_default=True, type=int,
              help="Maximum number of critic exchanges per run.")
```

To enable both critic rounds:

```bash
python3 scripts/run_eval.py \
  --critic-injection-points after_final_answer \
  --critic-injection-points after_critic_response \
  --critic-model claude-haiku-4-5-20251001 \
  --max-critic-rounds 2
```

`--critic-injection-points` uses Click's `multiple=True`, which requires the flag
to be repeated rather than space-separated. Both values must be present for the full
two-round exchange; omitting `after_critic_response` gives the original single-round
behaviour.

## 3. FA: FINAL ANSWER Marker Enforcement

### 3.1 Why the marker matters

The system prompt instructs the agent to end every response with:

```
FINAL ANSWER: <answer>
```

`extract_final_answer()` in `harness/scorer.py` searches for this pattern
case-insensitively. If it is not found, the function falls back to the last
non-empty line of the response text. That fallback is unreliable:

- A reasoning sentence like "Therefore it is likely Bacillus subtilis." becomes the
  submitted answer.
- The LLM judge receives a reasoning fragment rather than a clean answer, and may
  grade it wrong even if the correct answer appears elsewhere in the response.
- The `predicted` field in `scores.json` contains a fragment that is hard to
  interpret in a comparison table.

Qwen3 trajectories omitted the marker in 2–4 of every 5 attempts. The harness
had no way to recover except silently using the fallback.

FA adds a feedback loop: if the marker is absent, the harness injects one user
message asking for it and loops. If the agent still omits it after a single
re-prompt, the harness accepts and logs a warning.

### 3.2 `_has_final_answer_marker` helper

**File:** [`harness/agent.py`](../../harness/agent.py)

```python
def _has_final_answer_marker(text: str) -> bool:
    """Return True if `text` contains a 'FINAL ANSWER:' line followed by content."""
    return bool(re.search(r"FINAL ANSWER:\s*\S", text))
```

The regex requires at least one non-whitespace character after the colon and any
whitespace. This means:

- `"FINAL ANSWER: Homo sapiens"` → `True`
- `"FINAL ANSWER:"` → `False` (nothing follows)
- `"FINAL ANSWER:   "` → `False` (only whitespace follows)
- `"Some text. FINAL ANSWER: 42\nMore text."` → `True` (mid-text match)

> **Why not case-insensitive?** `FINAL ANSWER:` is specified in the system prompt
> in all-caps, and the system prompt instructs the agent to use exactly that form.
> Case-insensitive matching (as used in `extract_final_answer`) is appropriate for
> the scorer, which must be robust to model variation. The marker detector here
> is about whether the model followed the instruction, so exact-case is correct.

### 3.3 `_final_answer_reprompted` flag

**File:** [`harness/agent.py`](../../harness/agent.py), `AgentRun.__init__`

```python
self._final_answer_reprompted: bool = False
```

This flag ensures the re-prompt fires at most once per run. Without it, every
successive `end_turn` without a marker would trigger another re-prompt, potentially
looping until `max_steps` is reached.

> **Note on initialisation:** This field was not in the original FA PR (#58) and
> had to be added as a follow-on fix in PR #59, which also contained CP
> (critic prompt improvements). Between the FA merge and the PR #59 merge, 4 tests
> in the suite were broken on main. This is recorded as a lesson in
> `SKILLS/code_learnings.md` L-19.

### 3.4 `_loop`: re-prompt and format_warning logic

**File:** [`harness/agent.py`](../../harness/agent.py), `_loop()` method

The marker check runs **after** the critic block and **before** the success return:

```python
# FINAL ANSWER marker enforcement: re-prompt once if missing;
# if still missing after the re-prompt, log a format_warning
# and accept the response.
if not _has_final_answer_marker(response.text):
    if not self._final_answer_reprompted:
        self._final_answer_reprompted = True
        self.messages.append({
            "role": "user",
            "content": [{
                "type": "text",
                "text": (
                    "Your previous response did not include a FINAL ANSWER: line. "
                    "Restate your conclusion as: FINAL ANSWER: <answer>"
                ),
            }],
        })
        continue
    self.logger.log("format_warning", {
        "reason": "FINAL ANSWER marker missing after re-prompt",
        "text_excerpt": response.text[:300],
    })

self.logger.log("status", {"status": "success", "final_message": response.text})
return AgentResult(status="success", ...)
```

Three paths through this code:

**Path A — marker present (happy path):**
`_has_final_answer_marker(response.text)` is `True`. The `if` block is skipped.
Fall through to `status=success`.

**Path B — marker absent, first time:**
`_has_final_answer_marker` is `False` and `_final_answer_reprompted` is `False`.
Set the flag, append the re-prompt user message, `continue` back to the top of the
`while True` loop. The agent will receive the user message, (re-)generate a
response, and we check again.

**Path C — marker absent, already reprompted:**
`_has_final_answer_marker` is `False` and `_final_answer_reprompted` is `True`.
The inner `if` is skipped. Log `format_warning` with the first 300 characters of
the response (enough context to understand what the agent said). Then fall through
to `status=success` — the harness accepts the response rather than looping further.

> **📦 Why accept on second failure rather than aborting?**
> A `resource_abort` or `max_steps` result means the problem was not solved.
> If the agent gave a correct answer but forgot the marker twice, aborting would
> waste a correct result. The `format_warning` log provides observability — post-hoc
> analysis can identify how often marker omission occurs and whether answers
> extracted via the fallback are nevertheless correct.

## 4. Order of operations in the `end_turn` branch

The `end_turn` branch now has three sequential checks. Understanding their order
is important because each can inject a `continue` that skips the others.

```
end_turn response received
    │
    ▼
[1] Critic check
    ├── fire_critic == True → inject critic, continue
    │                         (FA check and success return are skipped this iteration)
    └── fire_critic == False → fall through
    │
    ▼
[2] FINAL ANSWER marker check
    ├── marker absent, not yet reprompted → re-prompt, continue
    │                                       (success return is skipped)
    ├── marker absent, already reprompted → log format_warning, fall through
    └── marker present → fall through
    │
    ▼
[3] Success return
    log status=success, return AgentResult
```

Key consequence: if `fire_critic` is `True` on an `end_turn` response that also
lacks the marker, the critic fires and the re-prompt does **not** fire in the same
iteration. The agent's follow-up response (after the critic message) is another
`end_turn`, at which point the marker check runs fresh. This is the correct
behaviour — the critic injection message explicitly asks the agent to end with
`FINAL ANSWER: <answer>`, so the follow-up is expected to have the marker.

## 6. Trajectory Event Reference: New Roles

| `role` | Added in | Contents |
|--------|----------|---------|
| `critic` | PR #26 (original) | `model`, `critique`, **`round`** (new in CR2, 1-based) |
| `format_warning` | PR #58 (FA) | `reason`, `text_excerpt` (first 300 chars of response) |

Existing roles are unchanged. The `critic` event's new `round` field is
backwards-compatible — existing parsers that do not read `round` are unaffected.

`format_warning` is a new role. If a trajectory analysis script counts events by
role, it should handle `format_warning` gracefully (e.g. not crash on unknown
roles).

| `test_reprompts_once_when_marker_missing` | 2 `client.chat` calls; one re-prompt message; `result.final_message` contains `FINAL ANSWER` |
| `test_accepts_after_one_reprompt_with_format_warning` | 2 calls both lacking marker; one re-prompt; one `format_warning` log; `status=success` |

### Key fixture pattern

All CR2 multi-round tests use `_llm_response(f"FINAL ANSWER: answer{i}")` as their
mock response text. The `"FINAL ANSWER: "` prefix is mandatory: without it, FA's
marker check would consume an extra `client.chat` call from the `side_effect` list
(see `SKILLS/code_learnings.md` L-19).
