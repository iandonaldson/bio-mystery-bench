## Step 3 — Choose memory-efficient tools when RAM is limited

Always prefer lighter tools when available RAM is below the threshold for the heavyweight alternative.

| Task | Lightweight (preferred when RAM < threshold) | Heavyweight | RAM threshold |
|------|----------------------------------------------|-------------|---------------|
| RNA-seq quantification | **salmon** (~2 GB) or **kallisto** (~4 GB) | STAR (27 GB for human) | 16 GB |
| Short-read alignment | **bowtie2** (~3 GB for human) | BWA-MEM (~6 GB) | 8 GB |
| Long-read alignment | minimap2 (~6 GB) | — | — |
| scRNA-seq | **scanpy** (streams from disk) | Seurat in R (loads all into RAM) | 16 GB |
| Differential expression | **pydeseq2** or **edgeR** | DESeq2 in R (large objects) | 8 GB |

**salmon** and **kallisto** are pre-installed and are the preferred quantification tools for RNA-seq
when the full STAR genome index cannot fit in available RAM. They are also faster.

For salmon, build a decoy-aware index against the transcriptome (not the genome) to keep
memory under 4 GB for human:
```bash
# salmon index (transcriptome only, ~2 GB RAM)
salmon index -t /workspace/scratch/transcriptome.fa -i /workspace/scratch/salmon_index --threads $(nproc)
```

For kallisto, index RAM is ~4 GB for human transcriptome:
```bash
kallisto index -i /workspace/scratch/kallisto.idx /workspace/scratch/transcriptome.fa
```

## Step 4 — Abort if resources are genuinely insufficient

If — after considering all lighter alternatives — you determine that the problem cannot be solved
reliably with the available RAM, disk, or CPUs, call the `abort` tool rather than producing
a guess or a partial result.

**When to abort:**
- The minimum RAM for even the lightest appropriate tool exceeds available RAM by more than 20%
- Scratch disk is insufficient to hold required reference files + intermediate outputs

**Do not abort** if a lighter tool can get the job done — prefer salmon over STAR, scanpy over
Seurat, pydeseq2 over DESeq2 before deciding resources are insufficient.

When you call `abort`, be precise:
- State the specific step that requires more resources (e.g. "STAR genome indexing requires 27 GB RAM")
- Give the minimum RAM/disk/CPU that would allow the analysis to proceed
- Note whether a higher-resource machine would make the heavyweight tool preferable

## General approach

1. Assess environment and data (steps 1–2 above)
2. Form a hypothesis about what analysis is needed
3. Choose appropriate tools given available resources
3a. A command that exits rc=0 with empty stdout ran successfully but produced no
    results — do not assume the tool is absent. Use `which <tool>` or `<tool> --version`
    to confirm availability before attempting reinstallation.
    Remote BLAST (`blastn -db nt -remote`) can return empty output on network timeout;
    if output is empty, verify with `blastn -version` first, then retry the query or
    switch to a local approach before concluding the tool is absent.
3b. For BLAST searches, prefer the `blast_search` tool over calling `blastn`/`blastp`
    directly. It runs the query, saves full tabular results to
    `/workspace/scratch/blast_results.txt`, and returns a compact hit summary — keeping
    large BLAST outputs out of your context window.
    If `blast_search` returns rc=-1 (network timeout) and
    `/workspace/scratch/blast_results.txt` contains no hits, do not switch to
    alternative alignment approaches (e.g. downloading a reference genome and running
    minimap2 — alignment percentage is not a species identity metric). Instead:
    (a) try `Bio.Blast.NCBIWWW.qblast()` via Python (Biopython is installed; see
    `/workspace/skills/blast-search.md` §9 for the recipe), or
    (b) `sleep 290` in bash (5 minutes, counts as one step) then retry with a ≤150 bp
    query. Do not submit longer queries until a ≤150 bp probe succeeds.
3c. **TF identification from ChIP-seq peaks.** To identify the transcription
    factor (or candidate TFs) responsible for a set of ChIP-seq peaks, extract
    the peak-flanking sequences with `bedtools getfasta` (typically ±100 bp
    around the peak summit) and scan them against a curated motif database
    such as JASPAR or HOCOMOCO, using `pyjaspar` together with `Bio.motifs`
    PWM scoring or the JASPAR REST API. Manually counting k-mers in a hand-
    picked subset of peaks is not a substitute for a motif database scan and
    will not identify the responsible TF reliably. See
    `/workspace/skills/chipseq-tf-identification.md` for copy-pasteable recipes.
4. Work step by step, checking intermediate results
4a. If a `wget`, `curl`, or API call returns a transient error (HTTP 429, 503,
    connection reset, or empty response), wait 30 seconds and retry up to 3 times
    before switching to an alternative source or approach.
5. Cross-validate findings with multiple approaches when possible
6. Before stating your final answer, explicitly check any assumptions your
   analysis depends on. In particular:
   - When grouping samples using a gene signature score, verify the expected
     direction of regulation for each gene in that condition. Genes in a
     pathway signature are not always upregulated — e.g. a ferroptosis inducer
     may suppress protective genes (GPX4) rather than activate them.
   - When inferring a condition from sequence homology (BLAST), check that the
     top-hit annotations consistently reflect the experimental condition, not
     just species or tissue of origin.
   - When the problem provides multiple items to analyse (sequences, genes, samples,
     peaks), analyse ALL of them — not just the first few. Sampling only the first
     3 of 18 genes, for example, introduces bias and can produce a completely wrong
     conclusion if the remaining items tell a different story.
   - State what you assumed and confirm it with data before drawing your conclusion.

   **Functional interpretation of gene lists.** When the question asks what
   condition, pathway, or perturbation a list of differentially expressed genes
   (DEGs) reflects, use a recognised enrichment method against curated annotation
   databases — do not infer the condition from sequence composition, GC content,
   codon usage, or any other property of the gene sequences themselves. Acceptable
   approaches:
   - Over-representation analysis (ORA) of the DEG list against Gene Ontology
     (biological process / molecular function / cellular component) or curated
     pathway collections (MSigDB hallmarks, KEGG, Reactome), applying
     Benjamini-Hochberg FDR correction to the hypergeometric p-values.
   - Gene Set Enrichment Analysis (GSEA) on the full ranked gene list (by log2
     fold change or signed test statistic) against the same collections.
   - Gene Set Variation Analysis (GSVA / ssGSEA) when per-sample pathway scores
     are needed rather than a single ranked list.
   Inferring "the genes look AT-rich, so this must be condition X" or
   "these genes share a k-mer motif, so the perturbation is Y" is not a valid
   substitute for an enrichment test against an annotated database. See
   `/workspace/skills/deg-functional-enrichment.md` for copy-pasteable recipes.
7. State your final answer clearly as:

**FINAL ANSWER: <your answer here>**

Your answer must match exactly the syntax and formatting used in the question and its starting materials.
For example: if sample names appear as `Sample_01` in the data, use `Sample_01` — not `Sample01`,
`sample_01`, or `SAMPLE_01`. If the question specifies a particular format (e.g. binomial nomenclature,
a unit, a list style), follow it precisely. The scorer is exact-match; formatting errors count as wrong.

Then stop. Do not continue after stating your final answer.

## Step and context budget

Note: **this run has a 60-minute wall-clock time limit** in addition to the step limit.
Each remote BLAST call that times out consumes up to 10 minutes of that budget. A download
or computation that takes 10+ minutes counts as a single step. One step = one tool call,
regardless of how long it takes.

Every tool result ends with a progress footer:

```
[Progress: step X/N | elapsed Xs/3600s | context ~Yk tokens | Z steps remaining]
```

Treat both the step count and elapsed time as hard constraints, not suggestions:

- **Normal (< 75% of steps or time used):** Work freely; cross-validate as needed.
- **⚠ WARNING (≥ 75% of steps or time used):** You are approaching a limit. If a download or
  multi-step computation is already underway and likely to complete within the remaining budget,
  continue it. Otherwise, consolidate what you already know and begin drafting your final answer.
  Do not start entirely new lines of investigation.
- **⚠ CRITICAL (≥ 90% of steps or time used):** State your FINAL ANSWER immediately, using the
  best evidence gathered so far. A committed answer based on strong partial evidence is always
  better than running out of budget with no answer at all.
